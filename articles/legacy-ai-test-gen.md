## 1. はじめに

仕様書がなく、テストコードも存在しない「ブラックボックス化したレガシーコード」――多くの現場が抱えるこの問題は、リファクタリングやマイグレーションを試みるたびに「これ、触って本当に大丈夫か？」という恐怖と隣り合わせです。挙動を保証するテストがなければ、変更のたびに手動での回帰確認を強いられ、結局は「触らぬ神に祟りなし」でコードは塩漬けにされていきます。

この記事では、実在する成熟したJavaライブラリ **Joda-Time**（CVS時代からの開発履歴を持つ、実運用実績のあるdatetimeライブラリ）を題材に、あえて `SPECIFICATION.md` と `src/test/java` 配下のテストコードを全削除し、「仕様書ゼロ・テストゼロ」のレガシーコードを人工的に再現しました。そのうえで、Claude Code に「このコードを唯一の正として仕様を復元し、挙動を担保するテストを書け」と指示した結果、どこまで実用的なセーフティネットを自動構築できるかを検証しています。

検証用リポジトリはこちらで公開しています。

https://github.com/yuninaka/legacy-datetime-lab

## 2. 結論：定量的に何を達成したか

先に結果を示します。対象は仕様復元・テスト強化のスコープとして選定した **21個のコアクラス（約2,700行）** です。

| 指標 | Before | After |
| :--- | :--- | :--- |
| テスト件数 | 0件 | **530件**（全PASS） |
| Line Coverage (C0) | 0%（テスト自体が存在しない） | **93.65%**（2,522/2,693） |
| Branch Coverage (C1) | 未計測 | **78.63%**（835/1,062） |
| PIT Mutation Score | 未計測 | **77.15%**（1,448/1,877） |
| PIT Test Strength | 未計測 | **81.03%**（1,448/1,787） |
| GitHub Actions（JDK17・`mvn test`＋PIT） | 未整備 | **Passing**（初回グリーン: 1分39秒） |

補足として、「テストは書いたがカバレッジ目標もPITも仕込んでいない」段階（初回の指示直後）の値も載せておきます。ライブラリ全体（222クラス）を母数にした場合はLine Coverage 27.45% / Mutation Score 12%、その後コアパッケージ21クラスに絞り込んだ直後の値はLine Coverage 28.30%でした。ここから「JaCoCoの未通過メソッド一覧」と「PITの生存ミュータント一覧」を追加の指示としてフィードバックし、最終的に上表の数値まで押し上げています。

## 3. 実験環境と事前準備

- **対象コード**: Joda-Time 2.14.3（`org.joda.time` を `com.legacy.system.datetime` にリネームしたレガシーコード基盤）。Java 5をターゲットにした設計で、パッケージ全体では150以上のソースファイルを持つ実ライブラリです。今回の仕様復元・テスト強化はそのうち主要な21クラスに絞っています。
- **あえて行ったレガシー化**: `SPECIFICATION.md` の削除、`src/test/java` 配下の全テストコードの削除。
- **実行環境の制約**: サンドボックス環境にはJRE（`openjdk-25-jre-headless`）しか入っておらず、`javac` が存在しない状態からのスタートでした。`sudo` も使えないため、ポータブル版のTemurin JDK 17をダウンロードして展開し、`JAVA_HOME` を切り替える形でビルド環境を自前で用意しています。
- **`pom.xml` の年代物っぷり**: `maven.compiler.target=1.5`、テスト依存は `junit:junit:3.8.2`。JDK 17の`javac`は「Source option 5 is no longer supported」と一蹴してくるため、コンパイラ設定をJava 17へ、テストフレームワークをJUnit 3からJUnit 5（`junit-jupiter`）へ移行し、Surefireのバージョンも合わせて上げています。
- **使用ツール**: JDK 17 (Temurin) / JUnit 5 / JaCoCo 0.8.11 / PIT (pitest-maven) 1.15.3 + `pitest-junit5-plugin` / GitHub Actions。

## 4. なぜ達成できたか：指示設計のポイント

対話を何十往復もして少しずつテストを書き足してもらった、という進め方ではありません。実際に投げた指示は数える程度で、それぞれの指示に対してClaude Codeがファイル読解・テスト作成・実行・失敗の原因調査・修正・再実行というループを**自律的に何十周も回して完遂**しています。人間側が細かく手順を指示する必要がなかった、という点がポイントです。

### ① 「唯一の正」と「合格基準」を最初から明示する

最初の指示は次のようなものでした。

> 現在のソースコードを【絶対の唯一の正（仕様）】として扱ってください。`SPECIFICATION.md` を作成し、現状のコード挙動を担保するJUnit 5テストコードを作成し、`mvn test` を実行して全件PASSすることを確認してください。

「仕様書を書いて」ではなく「**このコードが仕様だ、逸脱するな**」と情報源を一意に固定したことで、Claude Codeが独自の思い込みで「本来あるべき挙動」を仕様書に書いてしまう余地をなくしています。後続の「90%以上のカバレッジを達成する」という指示も同様に、目標値と検証コマンド（`mvn clean test`）を数値・コマンドの両方で明確化しました。

### ② カバレッジではなくPIT（ミューテーションテスト）を本質指標に据える

C0/C1カバレッジだけを目標にすると、「行は通っているが `assertEquals` の引数が緩い」といった“空振りテスト”が量産されるリスクがあります。実際、今回もカバレッジ整備の初期段階ではPITの **Test Strength が49%** しかなく、カバーした行の半分近くで注入した疑似バグを検知できていませんでした。そこで「JaCoCoの未通過メソッド一覧」と「PITで生存したミュータント一覧」を機械的にフィードバックし、境界値（DSTの夏時間ギャップ/オーバーラップ、null引数、オーバーロードの分岐、シリアライズの往復）を狙い撃ちするテストを追加させたことで、Test Strengthを81%まで引き上げています。

### ③ CLIエージェントによるプロジェクト全体の一括把握

Claude Codeは `pom.xml`・150以上のソースファイル・JaCoCoのXMLレポートを横断的に読み、「どのメソッドのどの行が、なぜ通っていないか」を型情報込みで特定できます。たとえば `LocalDateTime` は内部的に `{year, monthOfYear, dayOfMonth, millisOfDay}` の4フィールドで表現されている、といった実装の詳細をソースから正しく読み取り、`size()` の期待値をそれに合わせて書く、といった芸当は静的解析力があってこそです。

一方で、**実際に手を動かしてみないと分からない誤りも普通に発生**しました。ここで気になるのが「AIは本当にこのコードの実際の挙動を検証してテストを書いているのか、それとも学習データに含まれる本家Joda-Timeの一般的な仕様をそれらしく“暗唱”しているだけではないか」という疑いです。今回、ソースコード自体は本家Joda-Time 2.14.3をパッケージ名リネームしただけで、ロジック上の改変は一切加えていません（`diff` で確認済み）。つまり「記憶で書いても、たまたま正解してしまう」状況だったわけですが、それでも実際には**最初の思い込みが外れて実行時に赤くなり、実データを見て修正する**という場面が何度も発生しています。

| 箇所 | 最初の思い込み（誤り） | 実行して判明した実際の挙動 |
| :--- | :--- | :--- |
| `LocalDateTime.size()` | 8フィールド（年〜ミリ秒まで個別）と想定 | 実際は内部的に4フィールド（`year`/`monthOfYear`/`dayOfMonth`/`millisOfDay`）で表現 |
| DST境界のテスト | 夏時間の遷移タイミングを勘違いして期待値を設定 | 実行して初めて正しい遷移時刻が判明し、期待値を修正 |
| `Interval` のゾーン依存 `equals` | デフォルトタイムゾーンをUTCと誤認 | 実際のJVMデフォルトゾーンはAsia/Tokyoで、比較結果が食い違い判明 |
| `MutableDateTime.setDate(ReadableInstant)` | 時刻部分も上書きされると誤認 | 実際は日付部分のみ変更され、時刻は保持される |

これらは意図的に仕込んだトラップではなく、通常の開発過程で実際に起きた「誤った思い込み → テスト失敗で発覚 → 実際のソース・実行結果を見て修正」という再現可能な実例です。トラップという人工的な仕掛けがなくても、**実行結果という一次情報に照らして自分の誤りを機械的に修正し続けたこと自体が、記憶への丸投げではなく実挙動の検証を行っていた証拠**だと考えています。人間の役割は、そのループの中で「この方向性で正しいか」を最後に検証することに集約されます。

## 5. CI自動化とセーフティネットの確立

生成した530件のテストとPITの設定を、`.github/workflows/test.yml` としてGitHub Actionsに組み込みました。

```yaml
- name: Set up JDK 17 (Temurin)
  uses: actions/setup-java@v4
  with:
    java-version: '17'
    distribution: 'temurin'

- name: Run tests (mvn clean test)
  run: mvn --batch-mode --no-transfer-progress clean test

- name: Run PIT mutation testing (mvn pitest:mutationCoverage)
  run: mvn --batch-mode --no-transfer-progress pitest:mutationCoverage
```

`mvn clean test` でJUnit 5テストとJaCoCoレポートを、続けて `mvn pitest:mutationCoverage` でミューテーションテストを実行し、両方のレポートをartifactとして保存します。実際にpushしてワークフローを走らせ、初回実行で **全ステップ成功・1分39秒でグリーンバッジ点灯** を確認しました。

> 余談ですが、このリポジトリは本家Joda-TimeのGitリポジトリをそのままベースにしているため、CVS時代からの実開発履歴（2,300件超のコミット）や、本家専用のCI設定・Dependabot設定もまるごと引き継いでいました。公開後にDependabotが本家のバージョン範囲で大量の更新PRを自動生成してくるという“事故”も実際に発生し、不要なワークフローとDependabot設定を削除するところまでが今回の後片付けの一部です。レガシーコードのフォークには、ソース以外の“歴史的負債”も付いてくるという教訓でした。

## 6. まとめ

- 仕様書もテストもないレガシーコードに対して、「このコードを唯一の正とせよ」という情報源の固定と、「カバレッジではなくミューテーションテストで質を測れ」という合格基準の明確化さえ与えれば、Claude Codeは対話の往復を最小限に、自律的な検証ループだけでテスト件数530件・Line Coverage 93.65%・PIT Test Strength 81%のセーフティネットを構築できました。
- 人間の役割は「泥臭くテストを書く」ことから、「エージェントに与える目標設定と、出てきた成果物・数値の妥当性を評価する」ことへとシフトしています。
- 一方で、これは裏を返せば「AIにテストを書かせて、それが本当に正しく検証できているかを人間がどう見抜くか」という新しい課題でもあります。今回は意図的な改変（トラップ）こそ存在しませんでしたが、実際の開発過程で「思い込みで書いた期待値が実行して初めて誤りだと判明し、修正する」というやり取りが繰り返されたこと自体が、記憶への丸投げではなく実挙動を検証しながらテストを組み立てていたことの裏付けになったと考えています。
- なお、今回の対象はDBアクセスも外部I/Oも持たない自己完結したライブラリであり、「ソースコードを唯一の正とする」という前提が素直に成立する、AIにとって比較的有利なケースでした。実際の業務システムでは、ソースに現れない暗黙知（ドメイン知識・運用上の慣習）、DBスキーマ側の制約（外部キー、トリガー、ストアドプロシージャ）、動的に組み立てられるSQL、非機能要件（性能・同時実行・セキュリティ制約）など、アプリケーションコードだけを読んでも復元できない仕様が数多く存在します。こうしたケースでは、ソース単独の静的解析に加えて、実際のDBを含めた結合テスト・多数の入出力パターンによる特性化テスト（characterization testing）や、スキーマ定義・運用ログを追加の情報源として取り込む対策が別途必要になると考えられます。
