## 1. はじめに

Windows の UI 自動化(pywinauto)で、グリッドの値をキーボードとクリップボードで読むテストを作った。
単発では 15 セルすべて正しく読めた。ところが 450 セルを読む反復にすると、**100 件を超えるセルが間違った値になった**(最初の実行で 204 件、私のバグを直した後でも 112 件)。例外は出ない。それらしい値が返るだけだ。

調べる過程で、**性質の違う 3 つの現象**に行き当たった。

1. 環境(エクスプローラ)が、クリップボードの取得を邪魔する(誤読は起こさない)
2. **自動テストがテスト対象のセルの内容を `C001` から `c` に書き換え、以降ずっと誤読が続く**
3. ごく稀に、前のセルの値を読む

ただし、**最初に見た 100 件超の誤読が、このうちどれで起きたのかは、確かめられていない**(4章)。この記事は、そこまでの調べ方の記録であって、謎の完全な解決ではない。

Delphi の画面テスト自動化が可能かどうかを論じる記事ではない。題材のアプリは Delphi 風のグリッドだが、得られた知見の中心は **Windows の UI 自動化一般**に通じるものだ。

検証コードと実行結果の生ログは、GitHub で公開している[^1]。

## 2. この記事の前提(先に限界を書く)

- 検証したのは **Lazarus 4.8(LCL)** で作った小さなアプリで、**Delphi(VCL)ではない**。RAD Studio が手元になかったため、`TEdit` / `TButton` / `TStringGrid` を持つ同構成のアプリを Lazarus で作った。VCL とは中身が別実装で、結果がそのまま VCL に当てはまるとは限らない
- 検証は **Windows 11 の 1 台**。各条件の測定回数は多くない(3 回程度)。「この環境ではこうだった」という記録として読んでほしい
- 検証に使ったのは、この記事のために作った汎用のテスト用アプリだけで、業務システムの実物には触れていない
- 「Delphi のグリッドは画面テストで詰まるのか」の結論は出していない。VCL 実機での確認が先だと考えている(別の記事で扱う)

## 3. 何を測ったか

テスト対象は、`TEdit`、`TButton`、`TStringGrid`(3 列 × ヘッダ 1 行 + データ 5 行、セル編集を有効)を並べただけのアプリ。ツールは pywinauto。

Delphi/VCL のグリッド(`TStringGrid`)は、事前の調べでは、セル自体が UI Automation 上の要素にならないとされている(VCL のグリッドに UI Automation 対応を追加するオープンソースが存在すること自体が、その裏付けと見られる)。今回の Lazarus 版で実際に UI ツリーを取ると、グリッドは子を持たない 1 枚のウィンドウとして見えた(VCL での確認は、まだしていない)。

| 見え方 | win32 バックエンド | uia バックエンド |
|---|---|---|
| `TStringGrid` | 子要素 0 | 子要素 0(サポートするパターンは `LegacyIAccessible` のみ) |

標準コントロール(ボタンやテキスト入力)は、クリックも入力も読み取りも成功した(6/6)。

そこでセルの値は、**外から**読むことにした。今回の記事で扱うのは、その中の 1 つ、次の方式だ。

> **方式 A**: キーボードで目的のセルへ移動し、Ctrl+C でコピーして、クリップボードから値を取る。

単発の結果は次のとおり。15 セルすべて正しく、1 セルあたり約 77ms だった。

## 4. 症状: 単発では通る。反復すると崩れる

同じ読み取りを 30 周(450 セル)繰り返した。

| | 結果 |
|---|---|
| 単発(15 セル) | **15/15 正しい** |
| 反復(30 周 = 450 セル、3 回) | **誤読 204 → 160 → 112**(実行ごとに変動)、読取失敗 2 / 1 / 6 |

誤読は、隣のセルの値(1 つ前の値など)だった。**例外は一切出ない**。それらしい値がそのまま返る。

これは「動かない」より悪い。自動テストが、間違った値を正しい値として合格にしたり、正しい値を不合格にしたりする。

最初の実行の 204 件には、私自身のバグが混ざっていた。`Ctrl+Home` が LCL のグリッドでは行だけを先頭に戻し、列は戻さない、という挙動を見落としていたのだ。単発実行では初期位置が左上なので偶然通り、反復して初めて発覚した。そのバグを直しても、誤読は 100 件以上残った。**単発で通ったことは、何の保証にもならなかった**。

**この 100 件超の誤読が何によるものかは、確かめられていない。** 事実として言えるのは、次のことだけだ。

- 生ログが残っているのは、最後の実行(112 件)だけ(`demo/04_stability.out.txt`)。204 件と 160 件は、当時の出力を書き留めたもので、生ログは残っていない
- 物理入力の監視(5章)を作った後の測定でも、誤読は 0 件の回から 335 件の回まで大きくばらついた。当時は理由が分からなかった
- 7章の修飾キー喪失は、こうした大量の誤読を起こしうる機構だが、**最初の実行が同じ機構だったとは確かめられていない**

## 5. 調べる前に、観測の足場を作った

原因を推測だけで決めつける前に、**他の可能性を客観的に潰せる手段**を用意した。

| 道具 | 潰せるもの |
|---|---|
| 低レベルフックで**物理入力を数える**(自動化が注入した入力は数えない) | 「人が触ったせいでは」 |
| **アプリ側のログ**(受け取ったキーと、コピー時のセルの内容) | 「キーが届いていない/遅れている」 |
| **クリップボードの更新通番と所有者**を 1ms 間隔で記録 | 「誰が、いつ書いたか」 |
| **故障注入**(アプリを人為的に止める、クリップボードを人為的に塞ぐ) | 「自然発生が稀で、比較できない」 |

**故障注入**とは、失敗を自然発生に任せず、わざと起こして再現する手法のことだ。ここでは、アプリを人為的に止めたり、クリップボードを人為的に塞いだりした。

この節以降の測定は、物理入力が 0 であることを確認したうえで行った(検知された回は無効として扱った)。4章の症状の測定は、この仕組みを作る前のものだ。

**この検証の進め方について**: この検証は、AI コーディングツールの Claude Code と協働して進めた。テスト用アプリと測定スクリプトの作成、測定の実行、ログの分析は Claude Code と分担し、仮説の採否と、環境への介入は私が判断した。ウイルス対策ソフトの保護の一時停止と、エクスプローラを閉じる操作は私自身が行い、レジストリの設定変更は、私の承認のもとで Claude Code が実行した。分析ツールの誤り(7章)や、予測が外れた話(8章)も、この協働の中で起きたことなので、そのまま書いている。この記事の下書きも Claude Code と作成した。数値は Claude Code が生ログと照合し、私自身も要所(冒頭の誤読数のうち生ログが残っている 112 件、対策 M0/M1/M2 の比較、用量反応の測定)を生ログで確認した。

## 6. 事例 1: クリップボードが開けない — 犯人は「開いているエクスプローラ」だった

**先に断っておくと、この事例は誤読の原因ではなかった。** クリップボードが開けなくてもリトライで読み取れ、誤読の件数とも相関しなかった(ウィンドウを 1〜4 個開けた測定でも、誤読は 0〜2 件だった)。それでも、環境の状態で自動化の結果が不安定になる例として、調べ方ごと書く。

**現象**: 読み取りの最中に、`OpenClipboard` が拒否される。1 回の実行(450 セル)で 24〜30 回。リトライで乗り切れるが、他のプロセスとの競合を意味する。

### 仮説 1: ウイルス対策ソフトのせいでは?

私の環境にはウイルス対策ソフトが入っていた。保護を一時停止して(私自身の操作で)測り直した。

| 保護 | 競合(回/実行) | 平均 |
|---|---|---|
| 有効 | 28 / 24 / 30 | 27.3 |
| 一時停止 | 22 / 15 / 18 | 18.3 |

約 3 割減ったが、**止めても 15〜22 回は残る**。主因ではなさそうだ。ただ、これだけでは決め手にならない。

### 推測で終わらせず、保持者を直接特定した

`OpenClipboard` が失敗した**直後**に `GetOpenClipboardWindow()` で、クリップボードを握っているウィンドウを記録した。失敗 68 件の内訳はこうだった。

| 保持者 | 件数 |
|---|---|
| **エクスプローラ**(`explorer.exe`) | **53(78%)** |
| Windows のクリップボード履歴・同期サービス | 4(6%) |
| 特定不能(`OpenClipboard(NULL)` で開かれた) | 11(16%) |
| ウイルス対策ソフト | **0** |

保持者にウイルス対策ソフトは一度も現れなかった。次に、クリップボード履歴・クラウド同期の設定を明示的にオフにしたが、競合は減らなかった(28.3 回。もともと既定でオフ相当だった)。

### explorer の中を調べる

explorer.exe の内部を調べると、クリップボード用の窓(hWnd)を持つスレッドは 4 本あり、**すべて「File Explorer Window」スレッド**だった。当時、エクスプローラのウィンドウが 4 つ開いていた。エクスプローラのウィンドウ 1 つにつき、クリップボード用の窓(hWnd)が 1 つ対応する、という関係だ。

### ここで、結論を一度弱めた

explorer の内部には、ウイルス対策ソフトを含む複数の DLL が読み込まれていた。保護の一時停止では、読み込み済みの DLL は外れない可能性がある。すると先ほどの「主因ではない」は、「保護機能の一時停止では減らなかった」までしか言えない。**explorer の中にあるウイルス対策ソフトの DLL の関与は、排除できていなかった**。

### 決め手: エクスプローラを全部閉じる

エクスプローラのウィンドウを、最小化されていたものも含めてすべて閉じた(閉じたつもりでも、最初の確認では通常表示の 2 つと最小化された 2 つが残っていた)。

| 条件 | 競合(回/実行) |
|---|---|
| エクスプローラが 4 つ開(保護の有効・一時停止、履歴・同期の設定によらず) | 15〜32 |
| **全部閉じる** | **0 / 0 / 0 / 0** |

explorer の中の DLL は読み込まれたままだったのに、競合は消えた。**DLL の存在は原因ではなかった**。

### 用量反応: 数を変えて確かめる

(用量反応とは、原因の量を変えて、結果がどう変わるかを見る調べ方のこと。ここでは、開いているウィンドウの数を変える。)

「1 つだけ開いたら」も測ったが、この 1 つは**別のプロセスに開いていた**(これまで 4 つが動いていた explorer とは別)。ウィンドウの数の効果と、プロセスの違いの効果が分離できていない。そこで、**同じ explorer プロセスの中に、同じフォルダを 1〜4 個**開いて測り直した(各水準 3 回)。

![エクスプローラのウィンドウ数と、クリップボード競合の回数(棒 = 平均、点 = 各回)](/images/ui-automation-silent-misread/fig2_dose_response.png)
*図: エクスプローラのウィンドウ数と、1 実行あたりのクリップボード競合の回数(棒 = 平均、点 = 各回)。値は `demo/06_rerun_no_interference.*.out.txt` から。下の表が同じ数値。*

| 開いたウィンドウ数 | 競合(回/実行) |
|---|---|
| 0 | 0 / 0 / 0 / 0 |
| 1 | 0 / 0 / 0 |
| 2 | 2 / 0 / 0 |
| 3 | 12 / 14 / 8 |
| 4 | 26 / 28 / 29 |

**2 個から 3 個で、急に立ち上がる**。線形ではない。

- **この環境での結論**: クリップボード経由で読む自動テストの実行端末では、エクスプローラを全部閉じておく(開くなら 2 個以下)
- **限界**: 各水準 3 回。「2 個までは無害」は、この環境での観測にすぎない。エクスプローラが何のためにクリップボードを読みに来るか(「貼り付け」の可否の更新などが有力)は、確かめていない

## 7. 事例 2: 修飾キーが落ちて、テストがデータを書き換えた

次に、誤読そのものを調べた。ドライバ側の観測だけでは、「キーが届かない」「遅れる」「クリップボードの古い値」を区別できない。そこで**アプリ側にログを足した**(受け取ったキーと、Ctrl+C のときのセルの内容)。

### 決定的なログ

CPU 全コアに負荷をかけた条件で、ある実行だけ大量の誤読が出た(26/450)。そのアプリ側のログがこれだ。

```
15:32:24.854 K vk=17 col=0 row=1     ← Ctrl キーが押された
15:32:24.859 K vk=67 col=0 row=1     ← 5ms 後、「C」が届いた。だが Ctrl+C なら "C" の行になるはずが、素の K 行
15:32:26.067 K vk=39 col=0 row=1     ← 次のキーまで 1.2 秒の空白
15:32:26.254 K vk=17 col=1 row=1
15:32:26.265 C col=1 row=1 cell=Item-1   ← こちらは正しい Ctrl+C の行
```

Ctrl+C が来たときは `C` の行として記録される作りになっている。ところが 1 行目は、Ctrl が押されているのに、`C` キーが **Ctrl なしの素の `C`** として届いていた。直後に約 1.2 秒の停止もあった。

素の `c` は、セル編集が有効なグリッドでは**文字入力**として働く。そのセル (col 0, row 1) の中身を追うと、こうだった。

| 周 | セルの内容 |
|---|---|
| 1〜4 周 | `C001`(4 回) |
| 5 周目 | 素の `c` が入力され、コピー自体が行われない(読取失敗) |
| 6〜30 周 | **`c`**(25 回) |

**自動テストが、テスト対象のセルを `C001` から `c` に書き換えていた**。以降 25 周(6〜30 周)、そのセルを読むたびに `c` が返る。誤読 26 件は、読取失敗 1 件と、この書き換え後の 25 周分だった。**1 回の欠陥が状態を永続的に壊し、以降ずっと誤読が続いた**。

仕組みは、こうだと考えている。アプリの処理が遅れている間に、ドライバは Ctrl+C の送信を終えて Ctrl を離してしまう。アプリが `C` を処理する時点では、修飾キーの状態が落ちている。

ここでも、いくつかの可能性を潰した。キーの欠落や順序の入れ替えはなかった(送ったキー列と受け取ったキー列が一致した)。前面ウィンドウの変化(フォーカス喪失)も、異常の時刻と対応していなかった。

### 分析ツール自体が誤っていた

この結論に至るまでに、私の分析ツールが誤っていた。最初は、「k 番目に送った Ctrl+C」と「アプリが受け取った k 番目の Ctrl+C」を突き合わせていた。Ctrl+C が 1 つ欠けると、以降の突き合わせが全部 1 つずつずれる。**390 件を、移動キーの不具合と誤分類した**。送ったキー列と受け取ったキー列を差分アルゴリズムで比べる方式に直して、初めて「Ctrl 修飾の喪失」という本当の姿が見えた。

### 対策を、故障注入で検証する

対策の案は 3 つ作った。

- **M0**: 現状(`Ctrl+C` を一括送信、先頭への移動に `Ctrl+Home`)
- **M1**: Ctrl を押したままにし、**クリップボードに結果が出るまで離さない**
- **M2**: M1 に加え、`Ctrl+Home` をやめ、**修飾キーを使う操作を Ctrl+C だけにする**(移動は PageUp と Home)

ところが、負荷をかけた自然発生の比較では、対策なし(M0)でも Ctrl 喪失が 1 件も出なかった(3 モード交互に 8 サイクル、各 3600 読取)。自然発生を再現できず、比較にならない。

そこで、アプリに**人為的な停止**を入れた(Ctrl キー押下の 7 回に 1 回、処理中に 800ms 止まる)。停止のタイミングが決定的なので、結果も決定的になる。

| モード | Ctrl 喪失 | セル書き換え | 誤読(300 読取あたり) |
|---|---|---|---|
| M0 | 42 | 194 | **202** |
| M1 | 0 | 0 | 36〜42 |
| **M2** | **0** | **0** | **0** |

- M0 は、停止に対して壊滅的だった
- **M1 だけでは不十分**。Ctrl+C は守れたが、`Ctrl+Home` の Ctrl が落ちて先頭に戻らず、誤読が残った
- M2 は 0。修飾キーを使う操作を 1 つだけに絞り、それも結果が出るまで押し続けるので、停止しても素の `c` が届かない
- **遅くならない**: 450 読取で、M0 が 23.4 秒、M2 が 20.7 秒

持ち帰りは、**「修飾キー付きのキー送信を避ける。残る 1 つは、結果が出るまで押し続ける」**。

ただし、**効果の確認は人為的な停止の下**で行った。自然発生した失敗に対して効くかは、確かめられていない。

## 8. コラム: 予測が外れた話

もう 1 つ、稀な誤読が残っていた。**アプリは正しいセルをコピーしたのに、ドライバは前のセルの値を受け取る**という現象で、13500 読取で 6 件(約 0.04%)。うち 2 件は、値が読めない失敗だった。

クリップボードの更新通番を記録すると、パターンがはっきりした。正常な読取では、通番はクリアの後に **+12** 進む。古い値を読んだときは **+6 で止まり**、値が読めなかったときは **+0** だった。

Lazarus 4.8 のソースを読むと、説明がついた。グリッドのコピーは、HTML とテキストを 2 回に分けて書く実装になっている。1 回のコピーが、クリップボードへの書き込み 2 回(各 +6)だ。1 回目の時点では、テキストはまだ前のコピーの値のままで、しかも **`OpenClipboard` に失敗しても再試行しない**。だから、他のプロセスとぶつかると、

- 1 回目でぶつかる → 何も公開されない(値が読めない、通番 +0)
- 2 回目でぶつかる → 前の値が残る(古い値、通番 +6)

ここで、**予測をした**。「読み取り側がクリップボードを(最後の 1 回を除いて)開かず、更新通番だけを見て完了を待てば、読み取り側との衝突はなくなり、誤読は消えるはず」。結果は逆だった。**同じ規模(13500 読取)の測定で、件数は 6 件から 23 件に増えた**。

ただし、この 23 件には、**1 つずれ続ける連鎖の 2 件目以降が少なくとも 8 件**含まれる。連鎖を 1 件と数えても最大 15 件で、従来方式の 6 件はすべて単発だった。「6 → 23」ほど劇的ではないが、減るどころか増えたことに変わりはない(物理入力が検知された無効な 2 回を除くと、10500 読取で 22 件、連鎖を 1 件と数えて最大 14 件)。衝突の相手は、読み取り側だけではなかったのだ。

この機構は、衝突を人為的に起こして確認できた。コピーの直後にクリップボードを 40ms 握ると、60 回すべてで値が読めなかった(通番 +0)。クリップボードを高速に開閉して妨害すると、古い値が 12 件出て、**12 件すべてが通番ちょうど +6** だった。

これは **Lazarus のコピー実装に固有**の可能性が高い。Delphi(VCL)の `TStringGrid` に Ctrl+C の標準機能があるかも、まだ確かめていない。この話は、次の記事に回す。

## 9. 学んだこと

1. **単発で通っても信用しない。反復する**。15/15 が、450 セルの反復では 100 件超の誤読になった(原因は確定できていない)
2. **黙って間違うのが、いちばん危険**。エラーが出ない失敗を、先に疑う
3. **推測ではなく、直接観測する**。ウイルス対策ソフトを疑ったが、保持者を直接特定して、犯人はエクスプローラだと分かった
4. **結論を弱める証拠が出たら、弱める。交絡を疑う**。「1 つ開いたら消えた」は、別のプロセスに開いていたため、ウィンドウ数の効果と区別できなかった(同じプロセスで測り直すと、1 つなら実際に無害だった。別プロセスは理由ではなかった)
5. **稀な失敗は、故障注入で決定的に再現する**。自然発生では比較できなかった対策を、人為的な停止で比べられた
6. **分析ツール自体を疑う**。390 件の誤分類は、突き合わせの方式の欠陥だった
7. **予測が外れたら、外れたと書く**。「開かなければ衝突しない」は、外れた

## 10. 実務での持ち帰り

- 数百〜数千回の反復で確かめる(単発の成功で判断しない)
- 物理入力を検知して、人の干渉を排除する
- 可能なら、アプリ側にログを足す(受け取ったキー、状態)
- 修飾キー付きのキー送信を避ける。残る 1 つは、結果が出るまで押し続ける
- クリップボード経由で読むなら、実行端末のエクスプローラを全部閉じる(開くなら 2 個以下)
- 重要な判定は、値を 2 回独立に取って一致を確認する
- 可能なら、クリップボードやキー注入に頼らない経路(アプリ側のテスト用フックなど)を検討する

## 11. まとめ(限界と、次に確かめたいこと)

- **誤読と直結すると確かめられたのは、修飾キー喪失(実証は 1 例)と、Lazarus のコピー衝突(約 0.04%)だけ**。クリップボード競合は、誤読とは相関しなかった。**最初に見た 100 件超の誤読が、このどれで起きたのかは未解決**(4章)
- **VCL では検証していない**。グリッドの Ctrl+C の有無、修飾キー喪失が VCL でも起きるか、Lazarus 固有のコピー衝突が VCL アプリにも当てはまるかは、未確認
- **1 台の環境で、各条件 3 回程度**。「エクスプローラは 2 個まで無害」などは、この環境での観測にすぎない
- **対策 M2 の効果は、人為的な停止の下での確認**。自然発生した失敗への効果は未確認
- 自然発生する衝突の相手(8章の「他のプロセス」)は、特定できていない
- 次回は、Delphi(VCL)のグリッドを、画面テストで実際に扱えるかを確かめたい
