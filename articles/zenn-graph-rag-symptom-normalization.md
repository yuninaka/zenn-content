## 1. 概要

### 1.1 やったこと(3行サマリ)

- 前回記事([グラフRAG × ベクトルRAG 個人実証:設備保全ナレッジベースで見えた限界](https://zenn.dev/yuninaka/articles/zenn-graph-rag-limitations))で「あえて未着手」とした、Symptomノードの名寄せ(表記ゆれで別ノードに分裂する問題)を実際に実装した
- 直したはずのCypher生成が想定通り動かず、プロンプトを直したら**別の場所に潜んでいたグラフ設計のバグ**(原因のクロス混入)が新たに発覚した
- そのバグを直したら精度評価のスコアは**数値上は下がった**。中身を見ると実際にはより正確な結果になっており、「スコアが下がる=悪化」ではないケースを実測した

### 1.2 結果だけ先に

| type別 | 名寄せ前 | 名寄せ直後(バグ入り) | クロス混入修正後 |
|---|---|---|---|
| graph | 0.80 | 0.70 | 0.70 |
| vector | 1.00 | 1.00 | 1.00 |
| **全体** | **0.89** | **0.83** | **0.83** |

数値だけ見ると「名寄せしたら悪化した」ように見えるが、実際には**以前のスコアの高さの一部が、別のバグ(クロス混入)による偶然の水増しだった**ことが判明した。詳しくは本文で。

## 2. 前回のおさらい:Q1(0.00)の原因

前回記事では、「コンベアAでベアリングの異音は過去に何回報告されていますか?」という質問(期待:3回、R001/R006/R010)に対し、Agentが「1回」と誤答するケースを扱った。原因はSymptomノードが自由記述テキストのままMERGEされており、R001「搬送ベルトの異音・ローラー部のガタつき」、R006「ベルトの異音」、R010「ベアリングからの異音」が**意味的には同じ現象なのに別ノードに分裂**していたことだった。

このとき根本対応(カテゴリ辞書によるSymptom正規化)は「今後の課題」として記録するに留め、あえて未実装のまま公開した。今回はその続きを実装する。

## 3. 実装:カテゴリ辞書方式でSymptomを正規化

`build_knowledge_graph.py`に、あらかじめ定義した14カテゴリを追加した。

```python
SYMPTOM_CATEGORIES = [
    "異音", "振動", "圧力低下", "発熱", "温度上昇", "停止", "起動不良",
    "動作異常", "位置精度低下", "冷却能力低下", "バッテリー低下",
    "部品損傷", "汚損・劣化", "その他",
]
```

抽出プロンプトに「この一覧から最も近いものを1つ選ぶ」という`symptom_category`フィールドを追加し、Symptomノードはこの**カテゴリ値でMERGE**するよう変更した。報告書原文に近い自由記述(従来の`symptom`)は情報として失わないよう、`HAS_SYMPTOM`関係の`detail`プロパティに保持することにした。

```cypher
MERGE (s:Symptom {name: $symptom_category})
MERGE (r)-[h:HAS_SYMPTOM]->(s)
  SET h.detail = $symptom
```

Equipmentノードの名寄せ(前々回の修正)と同じ考え方で、「自由記述ではなく統制された値でMERGEする」というパターンの再適用である。

## 4. つまずき1: Cypher生成LLMがカテゴリの意味を理解しない

実装直後にQ1を再評価したところ、スコアは0.00のまま変化しなかった。生成されたCypherを見ると、原因は一目瞭然だった。

```cypher
MATCH (r:ReportEvent)-[:OCCURRED_ON]->(e:Equipment {name: 'コンベアA'})
MATCH (r)-[:HAS_SYMPTOM]->(s:Symptom {name: 'ベアリングの異音'})
RETURN count(r) AS occurrence_count
```

`Symptom.name`にはグラフ側では確かに`'異音'`という値しか存在しないのに、LLMは質問文の言葉(「ベアリングの異音」)をそのまま`name`に当てはめてしまっていた。`GraphCypherQAChain`のデフォルトのCypher生成プロンプトは、スキーマの型情報(プロパティ名と型)は渡すが、「このプロパティは統制語彙である」という**ドメイン固有の意味論**までは伝えない。グラフの構造を直しても、それを問い合わせるLLM側が構造の意図を知らなければ意味がない、ということを実感した。

対策として、`GraphCypherQAChain.from_llm(cypher_prompt=...)`[^1]でCypher生成プロンプトを差し替え、カテゴリ一覧と「質問文の症状表現を、意味的に最も近いカテゴリへマッピングしてから完全一致で検索すること」を明示的に指示した。

```python
CYPHER_GENERATION_TEMPLATE = """(...)
重要: Symptom.name は自由記述ではなく、以下のカテゴリ一覧からのみ選ばれた統制語彙です。
質問文にどんな症状の言葉が出てきても、必ずこのカテゴリ一覧の中から意味的に最も近いものを
1つ選び、name プロパティの完全一致で問い合わせてください(部分一致・CONTAINSは使わない)。

カテゴリ一覧: {categories}
(...)
"""
```

これでCypherは`Symptom {name: '異音'}`を正しく生成するようになり、Q1は`count=3`という正しい値を返すようになった。ここまでは狙い通りの展開だった。

## 5. 発覚した新バグ:原因のクロス混入

ところが、他の質問(以前は満点だったQ5・Q9)のスコアを確認したところ、異変が起きていた。

コンベアBの停止原因を尋ねるQ5で、実際に返ってきた原因一覧が以下の通りだった。

```
搬送物の詰まりによる過負荷            ← 実はコンベアA(R003)の原因
グリース切れによる可動部の摩擦抵抗増加   ← 実は搬送ロボット1号機(R013)の原因
床面の反射マーカーの汚損...          ← 実は搬送ロボット2号機(R016)の原因
圧力センサー(PS-11)の故障           ← 実は圧縮機A(R027)の原因
投入量制限センサーの故障...          ← 実はコンベアA(R030)の原因
```

**コンベアBについて聞いているのに、他の設備の原因が大量に混ざっていた。**

Q9(ポンプ3号機の吐出圧力低下の原因)でも、原因ごとの発生回数が実態(各1回)ではなく**全部「4」**という不自然な値になっていた。

### 原因: `CAUSED_BY`をSymptomから張っていた

グラフのスキーマは元々こうなっていた。

```
ReportEvent -[:HAS_SYMPTOM]-> Symptom -[:CAUSED_BY]-> Cause
```

Symptomが自由記述だった頃は、たまたまSymptomノードが実質「1インシデント専用」になっていたため気づかなかったが、Symptomをカテゴリ化して**複数の設備・複数のインシデントが同じノードを共有する**ようになった瞬間、この設計の欠陥が露呈した。

```cypher
MATCH (r:ReportEvent)-[:OCCURRED_ON]->(e:Equipment {name: 'コンベアB'})
MATCH (r)-[:HAS_SYMPTOM]->(s:Symptom {name: '停止'})
MATCH (s)-[:CAUSED_BY]->(c:Cause)
RETURN DISTINCT c.name AS 原因
```

このCypherは一見「コンベアBの、停止という症状の、原因」を絞り込んでいるように読めるが、実際には2つ目の`MATCH`でEquipmentの条件はすでに`r`の絞り込みにしか使われておらず、3つ目の`MATCH (s)-[:CAUSED_BY]->(c)`は**共有ノードである`s`から辿れる、あらゆる`Cause`**を無条件に返してしまう。`s`(「停止」というSymptomノード)には、コンベアB以外の設備の「停止」インシデントも同じノードとして繋がっているため、そちらの原因まで一緒に引っ張られてしまうわけだ。

### 対応: `CAUSED_BY`をReportEvent起点に変更

修正はシンプルで、`CAUSED_BY`の起点をSymptomではなくReportEventにするだけだった。

```
ReportEvent -[:HAS_SYMPTOM]-> Symptom(カテゴリ、共有)
ReportEvent -[:CAUSED_BY]-> Cause(その報告書固有)
```

こうすれば、`r`を通じて必ずその報告書固有の原因だけが辿れるようになる。修正後にCypherで直接確認したところ、コンベアBの停止原因は正しく2件(R008・R017)だけに絞り込まれ、ポンプ3号機の吐出圧力低下も各原因が正しく「1回ずつ」になった。

**「共有ノードを介した多段階の関係は、途中のノードで絞り込みがすり抜ける」というのは、グラフDB設計における典型的な落とし穴だと思う。今回はSymptomの正規化という一見無関係な変更が、この既存の設計上の欠陥を偶然あぶり出した形になった。**

## 6. 修正後もスコアは下がった:数字の見かけと中身の乖離

クロス混入バグを直したあと、精度評価を再実行した。結果はgraph平均0.80→0.70、全体0.89→0.83と、**数値上は悪化**した。しかし中身を1問ずつ確認すると、状況はもう少し複雑だった。

### Q9: 見かけ上0.50に低下、しかし中身はむしろ正確になった

修正前のQ9は、クロス混入バグのせいで各原因の発生回数が不自然な「4」になっていたにもかかわらず、スコアは1.00だった。理由は、Cypherの回答が不十分だったためAgentが`vector_search`ツールも追加で呼び出し、そちらの文章から偶然`R002`・`R007`・`R015`という報告書IDを拾えていたから、というものだった(前回記事の時点では気づいていなかった)。

修正後は、Cypherだけで「4つの原因がそれぞれ1回ずつ」という正確な回答を返せるようになった。しかし`graph_query`単体の回答が十分になった結果、Agentは`vector_search`を呼ばなくなり、そちらの文章に含まれていた報告書IDが回答から消えた。golden_qaの期待キーワードには`R002`等のIDが含まれているため、スコアは0.50まで下がった。

つまり、**「以前のスコアが高かったのは、実は不完全な回答をAgentが別ツールで偶然補っていたから」**であり、単体では以前から不十分だったことに、今回初めて気づけた。

### Q1: report_idを聞かれていないのに、golden_qaがreport_idを要求している

同じパターンはQ1にもあった。「コンベアAでベアリングの異音は**何回**報告されていますか」という質問に対し、修正後のCypherは正確に`count=3`を返し、回答も「過去に3回報告されています」と正しい。しかしgolden_qaの期待キーワードは`["3", "R001", "R006", "R010"]`と、**回数を聞いているのに報告書IDまで要求**しており、キーワード網羅率は0.25にとどまった。

これは実装のバグではなく、評価データ側の設計(「回数を聞く質問なのに、個別の識別子までキーワードに入れてしまった」)の問題だと考えている。

## 7. タグ付け方式は解決策になるか

残るQ5の減点(コンベアBの停止原因から、R005「モーター取り付けボルトの緩み」が漏れる)について、「1レポートに複数のSymptomカテゴリを持たせるタグ付け方式にすれば直るのでは」と考え、検討した。

R005の報告書本文は「コンベアBのモーターから異音および振動を確認」としか書かれていない。タグ付け方式にすれば、この文からLLMが「異音」と「振動」の両方のカテゴリを付与でき、振動関連の集計クエリでも正しく拾えるようになるはずだ。

しかし、Q5が本当に必要としていたのは「**停止**」というタグだった。これはR005自身の本文には一切登場せず、**後続のR017の本文**(「前回(R005)は取付ボルトの緩み、前々回(R008)はモーターのコイル絶縁不良が原因だったが...」)で初めて、R005が停止インシデントの一部として位置づけられている。

つまりこれは「1レポートあたり何個のタグを許可するか」という粒度の問題ではなく、**「1件ずつ独立に抽出する」か「同一設備の過去レポート履歴を踏まえて抽出する」か**という、もう一段深いアーキテクチャの選択の問題だった。後者を実現するには、抽出時に同一設備の過去レポートをコンテキストとして与える、あるいは抽出後に設備単位で一括して整合性チェックするフェーズを追加する必要がある。今回はこの実装までは踏み込まず、課題として記録するに留めた。

## 8. 得られた知見

### 8.1 「スコアが下がった」は「悪化した」と同義ではない

今回の一番の教訓はこれに尽きる。精度評価の数値だけを見て「名寄せを実装したら悪化した」と結論づけていたら、Q9のクロス混入バグにも、Q1のgolden_qa設計の問題にも気づけなかった。**スコアが動いたら、その差分がどの回答の変化によるものかを1問ずつ遡って確認する**という作業を、良くなった時も悪くなった時も同じ熱量でやる必要がある。

### 8.2 1つの設計変更が、無関係に見える別のバグを暴くことがある

Symptomノードの名寄せは、Cypher生成の精度を上げるための変更のはずだった。しかし実際には、それとは別の場所に潜んでいた「共有ノードを介した絞り込みのすり抜け」というグラフ設計上の欠陥をあぶり出す結果になった。旧設計でこのバグが表面化しなかったのは、Symptomが自由記述で実質分裂していたために**たまたま**共有ノードになっていなかっただけであり、正しさが保証されていたわけではなかった。名寄せという「良い変更」が、隠れていた別の問題を可視化した、という経験は印象的だった。

### 8.3 Agentのツール併用が、単体ツールの欠陥を覆い隠すことがある

`graph_query`単体では不完全な回答しか返せなかった時期、Agentは`vector_search`も追加で呼び出すことでgolden_qaのスコアを結果的に満たしていた。これは一見「Agentがうまく複数ツールを使い分けている」ように見えるが、実際には**graph_query側の欠陥を、Agentの柔軟性が偶然覆い隠していた**だけだった。ツール単体の実力を評価したい場合、Agentの複数ツール併用による「補完」を過信すると、個々のツールの弱点を見逃すリスクがある。

## 9. まとめと今後

Symptomノードの名寄せというピンポイントな修正から始まり、Cypher生成プロンプトの調整、グラフ設計に潜んでいたクロス混入バグの発見と修正、そして評価指標自体の設計を疑うところまで、当初想定していたより何段階も深い検証になった。数値だけを見れば「0.89→0.83」で後退しているが、実態としては「以前は気づいていなかった2つの欠陥(グラフのクロス混入、golden_qaの設計)」を発見できた、価値のある回り道だったと考えている。

残った課題は次の2つ。

1. **golden_qaの期待キーワード設計の見直し**: 「何回か」を聞く質問にreport_idを要求しない、といった質問の意図と評価基準の整合性を洗い出す
2. **同一設備の過去レポート履歴を踏まえた抽出**: R005/R017のように、後続のレポートが過去のレポートの位置づけを更新するケースに対応する、より高度な抽出アーキテクチャの検討

いずれも実装には踏み込まず、`docs/troubleshooting_log.md`に記録するに留めている。次回、どちらかに着手する形で続きを検証したい。

[^1]: `GraphCypherQAChain.from_llm()`は`cypher_prompt`にカスタムプロンプトを渡せる。クラス定義は[LangChain APIリファレンス(GraphCypherQAChain)](https://python.langchain.com/api_reference/community/chains/langchain_community.chains.graph_qa.cypher.GraphCypherQAChain.html)を参照(なお本文中でも触れた通り、このクラス自体は`langchain-community`パッケージの一部として非推奨化が進んでおり、将来的には`langchain-neo4j`パッケージ版への移行が案内されている)。
