## 1. 概要

### 1.1 やったこと(3行サマリ)

- 当初検討した「設備ごとに全履歴を1プロンプトに詰め込む」方式は、件数が数万件規模に増えると破綻すると判断し、**新しいレポート自身の文中にある後方参照だけを見て、参照先レポートを軽量に差分更新する**設計に変更した
- 実装後、この方式自体にも「緩い言及を拾いすぎる」という新たな誤り(false positive)が見つかり、それも合わせて修正した

## 2. 前回までのおさらい:1件ずつ独立抽出の限界

前回記事では、Symptomノードの正規化(カテゴリ辞書化)を実装したものの、Q5(コンベアBの停止原因)だけは直せなかった。原因はこうだった。

- R005(コンベアB)の本文は「モーターから異音および振動を確認」としか書かれておらず、単体で見れば「異音」カテゴリへの分類は妥当
- しかし後続のR017の本文には「コンベアBが再び停止。**前回(R005)は取付ボルトの緩み**、前々回(R008)はモーターのコイル絶縁不良が原因だったが...」とあり、R005は実質的に「停止」インシデントの一部として位置づけ直されている
- この情報はR005自身の本文には存在せず、**後から書かれたR017の本文にしかない**

これは「1レポートに複数タグを許可するか」という粒度の問題ではなく、「レポートを1件ずつ独立に処理するか、同一設備の過去レポート履歴を踏まえて処理するか」という、もう一段深いアーキテクチャの選択の問題だと結論づけていた。

## 3. 当初案:設備ごとに全履歴を1プロンプトに渡す方式 → 不採用

最初に考えたのは、抽出とは別に「設備ごとの整合性チェックパス」を追加する案だった。8設備それぞれについて、その設備の全報告書本文と1パス目の抽出結果をまとめて1回のLLM呼び出しに渡し、「後続レポートの言及を踏まえて各report_idのカテゴリを再判定する」というものだ。

実装に入る前に、この設計をレビューして不採用にした。理由は**スケールしない**からだ。

- **コンテキストウィンドウの限界**: 設備あたりの履歴が数万件に増えれば、いずれLLMのコンテキスト長を超える
- **精度の劣化**: 仮に収まったとしても、大量のテキストの中に埋もれた関連情報をLLMが見落とすリスクが増える("lost in the middle"問題)
- **コストの増大**: 履歴が増えるほど毎回のプロンプトが長くなり、処理コストが線形以上に増えていく

「設備の全履歴を毎回読み直す」という設計そのものが、データ量に対してスケールしない構造だった。

## 4. 採用した設計:後方参照検出・差分更新方式

代わりに採用したのは、**新しいレポート自身の文中に、過去レポートへの明示的な言及があるかどうかだけを見る**方式だ。

幸い、このデータセットの報告書は「前回(R005)は...」のように、過去の報告書IDを本文中に明示的に書く慣習になっている(実務の点検記録でもよくある書き方だと思う)。これを利用し、既存の抽出プロンプトに`backreferences`という項目を追加した。

```json
{
  "equipment": "設備名",
  "symptom": "...",
  "symptom_category": "...",
  "cause": "...",
  "action": "...",
  "part": "...",
  "backreferences": [
    {"report_id": "本文中に明示的に登場する過去の報告書ID(例: R005)",
     "implied_category": "その過去の報告書について、本文の記述から今回追加で分かった症状カテゴリ"}
  ]
}
```

`backreferences`が見つかった場合のみ、参照先の`ReportEvent`に軽量な追加`HAS_SYMPTOM`関係を差分更新する。

```cypher
MATCH (r:ReportEvent {report_id: $ref_report_id})
MERGE (s:Symptom {name: $implied_category})
MERGE (r)-[h:HAS_SYMPTOM]->(s)
  SET h.detail = coalesce(h.detail, $implied_category),
      h.inferred_from = $source_report_id
```

`inferred_from`プロパティに参照元のreport_idを入れておくことで、「その報告書自身の記述による分類」か「後続レポートの言及による推定分類」かをグラフ上で区別できるようにした。

この設計のポイントは、**レポート1件を処理するコストが、その設備の履歴総件数に依存しない**ことだ。新しいレポートを読むときに見るのは、そのレポート自身の文章だけ。過去の履歴を毎回読み直す必要がないので、履歴が何万件に増えても1件あたりの処理コストは一定のままになる。

## 5. 結果:R005が正しく2つのカテゴリを持つようになった

再構築後、実際にNeo4jを確認したところ、狙い通りの結果になった。

```
R005 -[:HAS_SYMPTOM]-> Symptom(異音)     detail: "異音および振動"
R005 -[:HAS_SYMPTOM]-> Symptom(停止)     detail: "停止"  inferred_from: "R017"
```

Q5(コンベアBが停止した原因)の生成Cypherが「停止」カテゴリでR005・R008・R017の3件を正しく拾えるようになり、scoreは0.75→1.00に改善した。

## 6. 実装した機能自身に見つかった誤り:緩い言及を拾いすぎる問題

ここで終わりにしても良かったが、念のため他のレポートの`backreferences`も一通り目視で確認したところ、**明らかにおかしい抽出**を見つけた。

R035の本文はこうなっている。

> ポンプ3号機で吐出圧力の低下を確認。過去に4回類似トラブル(R002, R007, R015, **R022**関連)が発生していることから、根本的な設計上の余裕不足を疑い...

この文からR022への「圧力低下」backreferenceが抽出されていた。しかしR022自身の本文を見ると、話が違う。

> ポンプ3号機で異常振動を確認。**過去の圧力低下系トラブル(R002, R007, R015)とは異なる症状**。点検の結果、軸の芯出し(アライメント)がずれていたことが原因と判明。

R022は自分自身の本文で「圧力低下系トラブルとは**異なる**」と明言している。それにもかかわらず、R035が4件を「類似トラブル」という緩い言葉でひとまとめにして言及していたため、抽出プロンプトがこれを額面通り受け取り、R022を圧力低下カテゴリにも紐づけてしまっていた。

実際にNeo4j上でも、R022は「振動」(自身の記述)と「圧力低下」(R035由来の誤り)の両方に紐づいており、Q9(ポンプ3号機の吐出圧力低下の原因)への回答が「合計5回発生」と、本来無関係なアライメントのずれまで含めるようになっていた。

**さらに厄介だったのは、この誤りが精度評価のスコアには一切現れなかったこと**だ。golden_qaのキーワード網羅率は「期待するキーワードが含まれているか」しか見ておらず、「余計な間違った内容が混ざっていないか」は評価対象外になっている。R005の正しい後方参照(スコアに現れて改善が見える)とは対照的に、こちらの誤りは静かに紛れ込んでいた。

### 対策:抽出条件の厳密化

`backreferences`の抽出条件に、否定例を明示的に追加した。

```
backreferencesは、本文が過去の報告書IDを明示的に挙げて、
「その報告書自身の症状が何だったかを個別に言い切っている」場合のみ含めてください。

- 含める例:「前回(R005)は取付ボルトの緩みが原因だった」
  → R005について今回の症状カテゴリと同じ扱いにできると言い切っている

- 含めない例:「過去に4回類似トラブル(R002, R007, R015, R022関連)が発生している」
  → 複数の報告書IDを「類似」「関連」とまとめて言及しているだけで、
    個々の報告書の症状を明言していない

- 参照先の報告書が「(過去のXXXとは異なる症状)」のように自ら今回の症状と
  異なると明言している場合は、たとえ後から緩く関連付けられていても
  絶対に含めないでください。

迷ったら含めない(空配列にする)ことを優先してください。
```

再構築したところ、R035のbackreferencesは空配列になり、R022は「振動」カテゴリのみに正しく戻った。一方でR005→R017の正しい検出(真陽性)は影響を受けず維持された。

## 7. 得られた知見

### 7.1 「件数が増えても壊れない」設計は、実装時のレビューで先回りできる

今回、当初案(全履歴を1プロンプトに詰め込む)を、実際にコードを書く前の設計レビューの段階で不採用にできたのは大きかった。もし実装してから「あとでデータが増えたら壊れる」と気づいていたら、作り直しのコストはずっと大きかったはずだ。「今のデータ件数(35件)で動くか」だけでなく、「件数が2桁、3桁増えても同じ設計のままで済むか」を実装前に自問する価値を実感した。

### 7.2 再現率(recall)を上げる変更は、適合率(precision)を落とすリスクとセット

後方参照検出は、R005のケース(拾えていなかった情報を拾えるようにする=再現率の改善)を狙って実装した。しかし同じ仕組みが、R022のケース(拾うべきでない情報を拾ってしまう=適合率の悪化)も引き起こした。「見逃しを減らす」方向の変更を入れるときは、「拾いすぎていないか」も必ずセットで検証する必要がある、という機械学習における基本的な教訓を、ルールベースに近いLLM抽出でも同じように踏んだ形になった。

### 7.3 評価指標が検知できない誤りは、目視でしか見つからない

R022の誤りは、9問のgolden_qaのスコアには一切影響しなかった。もしスコアの数値だけを信じて「0.86のままだから問題なし」と判断していたら、この誤りには気づけなかった。今回はたまたま`backreferences`の抽出結果を1件ずつ目視で確認したことで見つかったが、これは今回のデータ量(35件)だから可能だった作業でもある。**評価指標がカバーしていない失敗モードは確実に存在する**という前提で、定期的にサンプルを目視確認する習慣が必要だと感じた。

## 8. まとめと今後

「1件ずつ独立抽出 vs 過去レポート履歴を踏まえた抽出」という、記事2から持ち越した課題に対し、スケールする設計(後方参照の差分更新)で対応できた。さらにその実装自体に潜んでいた精度の問題も、目視確認によって発見・修正できた。

3本の記事を通じて見えてきたのは、グラフRAGの精度は「一発の完璧な設計」で決まるものではなく、**実装 → 評価 → 目視での深掘り → 設計の見直し、というループを何周できるか**で決まる、ということだった。

残っている課題は記事2から変わらず、次の2つ。

1. **golden_qaの期待キーワード設計の見直し**: 「何回か」を聞く質問にreport_idを要求しない、質問の意図と評価基準の整合性の洗い出し
2. **もっと広いデータでの検証**: 現状35件の合成データでの検証にとどまっており、件数が実際に数百〜数千件規模になったときの挙動(今回の後方参照方式が本当にスケールするか)は未検証
