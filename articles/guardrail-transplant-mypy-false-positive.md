## 1. はじめに

[前回記事](https://zenn.dev/yuninaka/articles/ai-review-philosophy)では、グラフRAG×ベクトルRAGシリーズ(全6回)とレガシーJavaリバースマイグレーションシリーズ(全4回)を振り返り、「テストやCIが通っている状態で、実は中身が間違っていた」という3つの静かなバグを紹介した。そこで固めたレビュー方針は、最終的に**CLAUDE.md(AIエージェントの個人設定ファイル)に恒久ルールとして書き加える**という形で資産化した。セッションが変わればAIの「学び」自体は引き継がれないが、外部のルールファイルに残しておけば、次のセッション・次の環境でも再現できるはずだ、という考え方だった。

この主張は、実はまだ検証していなかった。前回記事の題材は2つとも既存のシリーズの振り返りであり、「資産化した習慣を、実際に別のプロジェクトへ持ち込んだらどうなるか」は試していなかったからだ。

その後、別の検証(Azure OpenAI/AI Search/Cosmos DBを使ったRAG構築)で、[「レビューをやめた話」](https://zenn.dev/singularity/articles/stopped-reviewing-my-code)という記事を参考に、「読まなくても壊れないコードベース」を目指した品質ゲート(Ruff strict・mypy strict・vulture・ローカルとCIで共通のチェックスクリプト)を整備する機会があった。この実践は前回記事の2つのシリーズとは別の、3つ目のプロジェクトでの出来事だ。整備した内容は、再利用できる形でCLAUDE.mdとテンプレート一式に落とし込んでおいた。

今回、この品質ゲートのテンプレートを、前回記事で扱ったグラフRAGシリーズのリポジトリ(LangChain・Neo4j・ChromaDB・pydanticベースのモデルという、元プロジェクトとは全く異なるスタック)にそのまま移植してみた。**「資産化すれば移植できる」という前回記事の主張は、本当に成り立つのか**。この記事はその実地検証の記録であり、結果は「おおむね成り立つが、単純なコピペでは済まなかった」というものだった。

## 2. 移植したもの、移植できたもの

再利用可能な形で用意していたのは、次の3点だった。

- `scripts/ci_check.sh`: pytest → ruff → mypy strict → vulture(report-only)を1スクリプトに集約したもの
- `pyproject.toml`のRuff/mypy設定スニペット(`select`に`C90`/`PLR`/`N`/`B`/`ANN`を追加、mypy `strict = true`)
- CLAUDE.mdのテンプレート(PR前品質チェック・テストカバレッジの観点・noqa運用ルール)

移植先のリポジトリは、`requirements.txt` + `venv`でのpip運用のまま、テストが1件もなく、Ruff・mypy・CIのいずれも未設定という状態だった。この状態にテンプレートを適用しようとして、最初の判断が必要になった。

**テストが0件だと、pytestはゲートとして機能しない**。`pytest tests/`は収集0件でexit code 5を返すが、これは「全チェック通過」の空虚な緑にしかならない。既存の唯一の純粋関数(`keyword_coverage`というキーワード網羅率の計算関数)に対して最小限のテストを4件追加し、ゲート自体に意味を持たせてから先に進んだ。

もう1つ、当初の計画も変える必要が出た。最初は「今回は基盤整備のみ行い、既存コードへの指摘(Ruff/mypy導入直後に検出される分)は修正せず報告に留める」という方針で進めるつもりだった。しかし実際にRuffとmypyをゲート化した状態でチェックを走らせると、既存コードだけで43件・41件の指摘が出た。この状態でこのPR自体をマージすれば、**CIは最初から赤い状態でmainに乗ることになる**。「基盤整備だけ」という当初のスコープと矛盾したため、ここで一度立ち止まり、「既存の指摘も含めて今回のPR内で解消する」方針に切り替えることを確認してから作業を続けた。計画は状況が変われば見直してよく、見直したこと自体を記録に残しておくことが大事だと思う。

## 3. ガードレール自身が「静かに嘘をついた」瞬間

ここからが本題。前回記事の3つの実例は、いずれも「テストやCIが緑なのに中身が間違っていた」という**偽陰性**(本当は問題があるのに、ゲートが見逃す)の話だった。今回見つかったのは、その裏返しの**偽陽性**(問題がないのに、ゲートが赤くする)だった。

### 3.1 mypyが「存在しないはずの引数」を指摘したが、コードは正しかった

移植先のコードには、LangChainの`ChatAnthropic`クラスを次のように呼び出す箇所があった。

```python
llm = ChatAnthropic(model="claude-sonnet-4-6", temperature=0)
```

mypy strictを有効にした状態でこれを流すと、次のエラーが出た。

```
error: Unexpected keyword argument "model" for "ChatAnthropic"  [call-arg]
```

`model`という、公式ドキュメントにも出てくるごく普通のキーワード引数が「存在しない」と言われている。ここでもし、mypyのエラーメッセージをそのまま信じて「引数名が間違っているのだろう」と判断し、コードの方を書き換えていたら、正しく動いていたコードを壊すところだった。前回記事で立てた方針(5.3: 検証はAIやツールの出力を経由しない、独立した手段で行う)は、AIの説明だけでなく、**ツールの警告に対しても同じ姿勢で臨む必要がある**ということに、ここで気づいた。

独立した手段での確認として、実際にインストールされている`ChatAnthropic`クラスをその場でimportし、pydanticのモデルフィールドを直接調べた[^1]。

```python
from langchain_anthropic import ChatAnthropic
fields = ChatAnthropic.model_fields
print(fields["model"])
# annotation=str required=True alias='model_name' alias_priority=2
```

`model`は実在する、必須のフィールドだった。つまりmypyの指摘の方が誤りだった。原因は、`ChatAnthropic`がpydanticの`BaseModel`を継承したクラスで、コンストラクタのキーワード引数がpydanticのフィールド定義から動的に生成される構造になっている点にあった。mypyはこの動的な生成を静的には追えず、コンストラクタが引数を一切受け取らないかのように誤認していた。

解決策は`# type: ignore`で黙らせることではなく、mypyにpydanticの構造を教える公式プラグインを有効にすることだった。

```toml
[tool.mypy]
plugins = ["pydantic.mypy"]
```

これで誤検知は解消した。**「テストが通る」が「正しい」の証明にならないのと同様に、「型チェックが落ちる」も「コードが間違っている」の証明にはならない**。ゲートが赤くなったら、まず「ゲート側の前提が今回のコードと噛み合っているか」を疑うところから始める必要がある。

### 3.2 「型を正確に表現できない」ときの、noqaという名の誠実な妥協

もう1件、性質の違う判断が必要になった箇所があった。LangChainの`create_agent()`が返す型は、`create_agent`自身が持つ型変数(`ResponseT`等)に依存する、`CompiledStateGraph[...]`という深いジェネリック型になっている。これをそのまま組み立てて返すだけの関数に対して、型引数を正確に再現しようとすると、関数の中身に対して不釣り合いなほど複雑な型注釈が必要になる。

```python
def build_agent() -> Any:  # noqa: ANN401
    llm = get_llm()
    tools = [build_vector_tool(llm), build_graph_tool(llm)]
    return create_agent(llm, tools, system_prompt=SYSTEM_PROMPT)
```

ここで`Any`を使う判断は、3.1とは違い「ツールの誤検知を正す」話ではない。正確な型注釈を書こうとすると、`create_agent`自身が持つ型変数に依存する深いジェネリック型をそのまま書き写す必要があり、この関数がやっていること(組み立てて返すだけ)に対して不釣り合いに複雑になる。**そう判断した上での、正直な妥協**だ。この判断自体が正しいかどうかは意見の分かれるところだと思うが、大事なのは「面倒だから」ではなく理由をコメントとして残し、`# noqa`を使う際は必ず対象行に理由を明記する、というCLAUDE.mdのルールに沿って処理した点だ。理由が古くなったら、この抑制自体を削除する、というルールもあわせて適用している。

## 4. 「移植できた」の中身を、正直に切り分ける

ここまでの3件のうち、実は性質が違うものが混ざっている。

- **3.1(pydanticプラグイン)・3.2(Any+noqaの判断)は、今回のプロジェクトで初めて遭遇した、真の新規の摩擦だった**。テンプレート側のドキュメントにも事前の記載はなく、その場で調査して解決した
- 一方、移植の過程では`mypy src`が"Source file found twice under different module names"というエラーも出た。これは元プロジェクト(Azure RAGの検証)で以前遭遇したのと**全く同じ**エラーで、`src/__init__.py`を追加すれば解決するとすぐに分かった

3件目は一見「知識が再現した」ように見えるが、ここで正直に確認しておきたいことがある。この解決策は、テンプレート化した`docs/`や`templates/`のいずれにも**書かれていなかった**。今回すぐに気づけたのは、このセッション内で元プロジェクトの作業を直接記憶していたからであって、CLAUDE.mdやテンプレートファイルという「外部化された」知識を参照したからではない。もし本当に何も覚えていない、まっさらな別セッションでこのテンプレートだけを渡されていたら、このエラーにも3.1・3.2と同じように、その場から調査を始める必要があったはずだ。

前回記事の主張は「外部のルールファイルに残せば、次のセッション・次の環境でも再現する」というものだった。今回の結果は、その主張を**部分的にしか裏付けなかった**ことになる。移植したテンプレート自体(ci_check.shの構成、Ruff/mypyの設定方針、noqaの運用ルール)は確かに機能したが、個別の技術的つまずき(pydanticプラグイン、`src/__init__.py`、langgraphの深いジェネリック型)は、その都度その場で解決する必要があった。**習慣・型のルールは移植できる。個別の環境依存の落とし穴は、書いておかなければ再現しない**という、当たり前だが見落としがちな線引きが、今回実際に手を動かしたことで明確になった。

## 5. 得られた知見

### 5.1 ガードレールの「赤」も、鵜呑みにしてはいけない

前回記事の核心は「緑(テスト・CIが通る)は正しさの証明にならない」だった。今回の3.1はその裏返しで、「赤(型チェック・lintが落ちる)も間違っている証明にはならない」ということだ。静的解析ツールは、コードの実際の挙動ではなく、コードについての**ツール自身のモデル**を検査している。そのモデルが実態(今回で言えばpydanticの動的なフィールド生成)を正しく捉えられていなければ、赤信号は「ツールのモデルと実装が食い違っている」ことしか意味しない。ツールの指摘を鵜呑みにして実装を書き換える前に、独立した手段(今回であればライブラリのソースを直接読む)で裏を取る必要がある。

### 5.2 「移植できる」と「摩擦なく動く」は別の主張

テンプレートは実際に機能し、最終的にはこのプロジェクトのCI(GitHub Actions)も実際に緑になった[^2]。ただしそこに至るまでに、テンプレートが想定していなかった2つの技術的な壁(3.1・3.2)を、その場で診断・解決する必要があった。「移植可能」というのは「ゼロから作るより速く、より確実にたどり着ける」という意味であって、「何も考えずに動く」という意味ではない。この区別を曖昧にすると、次に同じ移植をする(あるいはAIエージェントに任せる)ときに、想定外の壁に対する心構えを失うことになる。

### 5.3 見つけた摩擦は、次のためにテンプレート側に書き戻す

4章で切り分けた通り、今回の摩擦のうち2件(pydanticプラグイン・langgraphの深いジェネリック型)は、まだテンプレート側のドキュメントに反映していない。この記事を書いた後、実際に`docs/python-quality-gates.md`にこの2件を追記する予定だ。前回記事の言葉を借りれば、これも「検証習慣を属人化させず、次のセッション・次の環境でも再現させる」ための資産化の一部であり、今回見つかった摩擦を放置すれば、次に同じテンプレートを別プロジェクトに適用したときにまた同じ調査を最初からやり直すことになる。

## 6. まとめ

前回記事で固めた「検証習慣をCLAUDE.mdに資産化する」という方針を、別プロジェクトへの実際の移植というかたちで初めて試した。結果は、テンプレート化した習慣(品質ゲートの構成・noqaの運用ルール)自体は機能した一方、個別の技術的なつまずき(pydanticプラグイン、深いジェネリック型の扱い)は書いておかなければ再現しない、という当たり前だが実感の伴う教訓だった。そして今回見つかった最大の収穫は、ガードレールという「検証する側」のツール自身も、時には静かに間違った信号を出す、という点だった。テストの green を疑うのと同じ姿勢で、lintやtype checkerの red も疑う必要がある。
