## 1. はじめに

消費税率変更のような、頻繁に改正が入る制度対応のテスト工程を任されるとしたら、どう備えるか。この手の案件で必ず出てくるのが、「税額計算のロジックは、当時の担当者しか経緯を知らないレガシーコードに埋まっている」という状況だ。仕様書はなく、テストもない。触れば動くので誰も触っていない。だが税率が変わる以上、いつかは触らざるを得ない。

こういうコードに手を入れる前提として、まず「保護テスト基盤」を作っておきたい。改修前の挙動をそのまま資産化しておけば、実際の税率変更作業に入ったときに「この変更で意図せず他の挙動まで壊していないか」を機械的に確認できる。これが**Characterization Testing**(ゴールデンマスターテスト)と呼ばれる手法で、テストの中に「正しさ」の判断を一切持たせず、「今の挙動と一致しているか」だけを見る。

この記事は、実際の案件コードの代わりに「経緯不明・引き継ぎ資料なし」という設定のレガシー風価格計算コードを自作し、そこにCharacterization Testingの型を適用してみた実務ノートだ。作ったコードはシンプルな1関数だが、実際にやってみると「入力パターンを広く機械的に洗い出す」ことの価値を、頭で理解しているのと手を動かして確認するのとでは、かなり違うということがわかった[^1]。

## 2. 題材: 経緯不明の価格計算コード

対象にしたのは、次のような`calculate_price`という1関数だ。

```python
def calculate_price(
    base_price: int, category: str = "normal", tax_rate: float = 0.10
) -> int:
    if base_price < 0:
        return 0

    tax = base_price * tax_rate
    if base_price % 10 == 5:
        tax_amount = math.floor(tax) + 1
    else:
        tax_amount = round(tax)

    total = base_price + tax_amount
    if category == "special":
        total -= 1

    return total
```

この関数には、ブラックボックス探索の過程で判明した「謎仕様」が複数ある。

- `base_price % 10 == 5`のときだけ、税額が切り上げ相当(`math.floor(tax) + 1`)になる。それ以外はPython標準の`round()`(銀行丸め/偶数丸め)
- `category == "special"`のとき、計算後の総額から1円引かれる。理由は不明
- `base_price < 0`のときは検証なしに`0`を返す。バリデーション漏れの可能性がある
- `"normal"` / `"special"`以外の未知のcategory値は、すべて`"normal"`と同じ扱いになる

なぜこうなっているのかは、このコード自身の設定として「わからない」ことにしている。実際の現場でも、こういうコードに対して「なぜこうなっているか」を推測で埋めるのは危険だ。まず挙動をそのまま固定するところから始める。

## 3. Characterization Testingの型(5ステップ)

今回実践した型は次の5ステップだ。

1. **対象範囲の特定**: 変更対象の入出力境界を決める(今回は`calculate_price`という1関数に絞った)
2. **入力空間の設計**: 中身を読んで「起こりうるケース」を頭で予測するのではなく、境界値・典型値・ゼロ・負数・未知の値を機械的に広く洗い出す
3. **ゴールデンマスター生成**: 設計した入力空間に対して実際にコードを呼び出し、返ってきた値をそのまま記録する「ブラックボックス探索」を行う。期待値を手で書かない
4. **保護テスト実装**: ゴールデンマスターとの一致だけを見るテストを書く。テストコード自体には「正しさ」の判断を一切持たせない
5. **改修時の運用**: 意図した変更(税率変更等)の際は、該当範囲だけゴールデンマスターを再生成し、変更理由を記録する

3〜4は言葉にすると当たり前に聞こえるが、実際にやってみると「入力空間をどこまで広く取るか」の設計がそのまま保護テストの検知力に直結する、ということが6章で具体的にわかる。

## 4. ブラックボックス探索で1032件のゴールデンマスターを作る

ゴールデンマスター生成スクリプトは、次の入力空間を機械的に組み合わせている。

```python
# base_price % 10 == 5 の分岐境界を広く踏むための値(0〜30・90〜110・990〜1010の全剰余)
_BOUNDARY_BASE_PRICES = [*range(0, 31), *range(90, 111), *range(990, 1011)]

# 典型的な価格帯
_TYPICAL_BASE_PRICES = [100, 500, 999, 1234, 1500, 2500, 9999, 12345, 100000]

# ゼロ・負数(バリデーション漏れの可能性がある領域)
_ZERO_AND_NEGATIVE_BASE_PRICES = [0, -1, -5, -10, -15, -100, -9999]

# "normal" / "special" に加え、未知の値・空文字・表記ゆれを含める
_CATEGORIES = ["normal", "special", "unknown", "", "SPECIAL", "special "]

# 旧税率(0.08)と現行税率(0.10)の両方
_TAX_RATES = [0.08, 0.10]
```

`base_price`・`category`・`tax_rate`の全組み合わせに対して実際に`calculate_price`を呼び出し、返ってきた値をそのまま記録する。実行結果は次の通りだ。

```
$ python3 -c "import json; print(len(json.load(open('tests/golden_master.json'))))"
1032
```

**1032件**。ここでのポイントは、生成スクリプトの中に「この入力ならこの値が返るはずだ」という期待値の記述が一切ないことだ。人間が予測して書いた値ではなく、実際に動かして観測した値だけが記録されている。

## 5. 保護テストの中身: 「正しさ」を一切判断しない

保護テスト側は、ゴールデンマスターの全件を`pytest.mark.parametrize`でパラメータ化し、一致を見るだけのシンプルな作りにした。

```python
def test_matches_golden_master(case: GoldenMasterCase) -> None:
    actual = calculate_price(case["base_price"], case["category"], case["tax_rate"])
    expected = case["result"]
    assert actual == expected, (
        f"挙動が変化しました: calculate_price("
        f"base_price={case['base_price']}, "
        f"category={case['category']!r}, "
        f"tax_rate={case['tax_rate']}) "
        f"は golden master では {expected} でしたが、実際は {actual} でした "
        f"(差分: {actual - expected:+d})"
    )
```

現行の実装に対して実行すると、当然だが1032件すべてpassする。

```
$ uv run pytest tests/test_characterization.py -q
1032 passed in 0.43s
```

## 6. デモ: 「善意のリファクタ」で60件検知——そして「たまたま」検知されなかった数件

ここからが本題。このコードに対して、レビューも通りそうな「単純化リファクタ」を1つ加えてみる。

```diff
-    tax = base_price * tax_rate
-    if base_price % 10 == 5:
-        tax_amount = math.floor(tax) + 1
-    else:
-        tax_amount = round(tax)
+    tax_amount = round(base_price * tax_rate)
```

`base_price % 10 == 5`のときだけ税額を切り上げ相当にする「意図不明な特殊ケース」をなくし、Python標準の`round()`に統一しただけの変更だ。コードは明らかにシンプルになった。これを実際に差し替えて保護テストを実行する。

```
$ uv run pytest tests/test_characterization.py -q
60 failed, 972 passed in 0.54s
```

1032件中**60件**を検知した。失敗は`base_price % 10 == 5`に該当する値に集中している。

| base_price | 失敗件数(最大12) |
|---|---|
| 5 | 12 |
| 15 | 6 |
| 25 | 12 |
| 95 | 0 |
| 105 | 12 |
| 995 | 0 |
| 1005 | 12 |
| 12345 | 6 |

ここで気になるのが、`15`と`12345`だけ失敗件数が半分(6件)になっていることだ。category6種×tax_rate2種=12パターンあるはずなのに、なぜ半分しか検知されないのか。実際の値を突き合わせて確認した。

**`base_price=15`(golden masterの記録値 → リファクタ版の実際値)**

| category | tax_rate=0.08 | tax_rate=0.10 |
|---|---|---|
| normal | 17 → 16(検知) | 17 → 17(**非検知**) |
| special | 16 → 15(検知) | 16 → 16(**非検知**) |
| その他4カテゴリ | 同様に検知 | 同様に非検知 |

`15 * 0.08 = 1.2` → 旧実装は`floor(1.2) + 1 = 2`、新実装は`round(1.2) = 1`で**不一致**。一方`15 * 0.10 = 1.5` → 旧実装は`floor(1.5) + 1 = 2`、新実装は`round(1.5) = 2`(偶数丸めで1.5は2に丸まる)で**偶然一致**してしまう。

`base_price=12345`はこの逆で、`tax_rate=0.10`側でのみ検知され(golden master 13580 → 実際13579)、`tax_rate=0.08`側は偶然一致して非検知になる(golden master 13333 → 実際13333)。

さらに表を見ると、`95`と`995`は失敗件数が**0**、つまり12パターン全てが非検知になっている。これは`15`・`12345`よりもう一段踏み込んだケースで、片方の税率だけでなく**両方の税率で偶然一致**してしまっている。

- `95`: `tax_rate=0.08`→旧`floor(7.6)+1=8`、新`round(7.6)=8`(一致)。`tax_rate=0.10`→旧`floor(9.5)+1=10`、新`round(9.5)=10`(9.5は偶数の10に丸まり一致)
- `995`: `tax_rate=0.08`→旧`floor(79.6)+1=80`、新`round(79.6)=80`(一致)。`tax_rate=0.10`→旧`floor(99.5)+1=100`、新`round(99.5)=100`(99.5は偶数の100に丸まり一致)

念のため検算しておくと、`base_price % 10 == 5`に該当する8つの値の失敗件数を合計すると`12+6+12+0+12+0+12+6=60`となり、`pytest`が報告した「60 failed」と完全に一致する。今回のリファクタによる差分は、すべてこの条件の内側に閉じている。

つまり、**もし税率を1パターンだけでテストしていたら、`base_price=15`の挙動変化を完全に見逃していた**可能性がある。旧税率・現行税率の両方を機械的に含めていたことで、`15`・`12345`のような「片方の税率でのみ一致してしまう」見逃しは防げた。ただし`95`・`995`が示す通り、**2税率を用意していても、両方でたまたま一致してしまう偶然までは防ぎきれない**。入力空間をどれだけ広く取っても、まだ見えていない偶然の一致が残りうる——これは手法の欠陥というより、保護テストそのものが持つ限界だと捉えている。広い入力空間を機械的に洗い出すことの価値は、こういう「たまたま一致してしまうケース」を減らせることにあるのであって、ゼロにできるという意味ではない。

## 7. 副産物: 探索で見つかった「謎仕様」をどう扱うか

ブラックボックス探索の過程で、2章で挙げた3つの「謎仕様」が機械的に洗い出された。

| 謎仕様 | 内容 |
|---|---|
| special時の-1円調整 | `category == "special"`のとき、総額から1円引かれる。理由不明 |
| 負数の扱い | `base_price < 0`で無条件に`0`を返す。バリデーション漏れの可能性 |
| 未知category値の扱い | `"normal"` / `"special"`以外はすべて`"normal"`扱い。バリデーションなし |

実案件でこの手の「謎仕様」を見つけたとき、その場で「これはバグだろう」「これは仕様だろう」とAIエージェントや実装者が判断して直す、という進め方は取らない。保護テストの役割は「正しさを判定すること」ではなく「現状の挙動を固定し、変更を可視化すること」であり、正しさの判断はテストの外、人間(業務有識者・元担当者等)の側に委ねる。ゴールデンマスター生成のような機械的な探索で挙動を一覧化し、確認材料として渡す、という運用にしている。

## 8. 意図した変更時のゴールデンマスター更新フロー

税率変更のような**意図した仕様変更**の場合は、ゴールデンマスターの全件を無条件に再生成してはいけない。無関係な範囲まで一括で再生成すると、意図しない別の変更まで一緒に「正解」として固定してしまう危険があるからだ。実運用では次の手順にしている。

1. 変更が影響する範囲を特定する(税率変更なら`tax_rate`に依存する全ケース、category追加なら該当categoryのケースのみ、等)
2. 影響範囲**だけ**を対象にゴールデンマスターを再生成する
3. 再生成した理由(どの仕様変更に対応するものか、いつ・誰が判断したか)をコミットメッセージまたはPR説明に記録する
4. 保護テストを実行し、影響範囲外のケースに差分が出ていないことを確認してからコミットする

## 9. まとめ

「経緯不明のレガシーコード」を題材に、Characterization Testingの型を最初から最後まで一通り動かしてみた。得られた実感は次の2つだ。

- **保護テストは「正しさ」を判断しない**からこそ、謎仕様を勝手に直さず、人間への確認材料として一覧化できる
- **入力空間を機械的に広く取る**ことの価値は、代表値サンプリングでは気づけない「偶然の非検知」(6章の`base_price=15`・`12345`)を実際に見て初めて実感できた。ただし`95`・`995`が示す通り、広げても防ぎきれない偶然は残る。境界値を機械的に広く取ることは「見逃しを減らす」ための投資であって、「ゼロにする」保証ではない

こうした制度対応の実案件に取り組むなら、まずはこの型を実際の対象コードに適用し、保護テスト基盤を先に固めるところから始めたい。
