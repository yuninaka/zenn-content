## 1. はじめに

[レガシーJavaライブラリの検証プロジェクト](https://github.com/yuninaka/legacy-datetime-lab)で、PMD CPD（重複コード検知）の抑制コメント8件を監査するタスクを、コーディネーター役のエージェントに任せました。実際の監査作業はそのコーディネーターがさらに別のサブエージェントへ委譲する、2階層構成です。

サブエージェントは実際に8クラスタ全件を監査し、CI検証まで完走して、詳細な最終報告を返していました——これは最上位セッション側では確認できていました。ところが、コーディネーター自身に「報告はちゃんと届いているか」と直接尋ねたところ、返ってきたのは意外な答えでした。

> Status check, answered honestly and without further digging: ... So right now I am not relaying a report at all — I have no report to relay yet, verified or otherwise.

**サブエージェントは確かに報告を出していたのに、その報告を受け取るはずのコーディネーター自身には届いていませんでした。** これが単発の偶然なのか、それとも構造的に起こりうる不具合なのかを、実務タスクを介さない最小構成で確かめた記録です。

検証の生ログ・再現手順は別リポジトリに公開しています。

https://github.com/yuninaka/claude-code-agent-delegation-repro

## 2. 結論：定量的に何を確認したか

| 検証 | 内容 | 結果 |
| :--- | :--- | :--- |
| 実務タスク（発端） | CPD抑制8件監査、サブエージェントへ委譲 | サブエージェントは完走・報告済みだが、コーディネーターは「受け取っていない」と回答 |
| 軽量再現・条件A | 「先に待機報告→フォローアップで本回答」を意図的に再現 | サブエージェントは正解を出したが、コーディネーターには届かず |
| 軽量再現・条件B | 「先に報告するな、一発で本回答を出せ」と明示指示 | **指示があっても早期チェックポイントは防げず**、条件Aと同じ症状が再発 |
| 軽量再現・条件C | 会話的な催促の代わりに`TaskOutput`で直接取得を試行 | **`TaskOutput`自体がコーディネーターのツール一覧に存在しなかった** |

3つの独立した試行すべてで、同じ症状（サブエージェント自身の最終回答は依頼元の会話には直接届くが、直接の依頼主であるコーディネーターには届かない）を確認しました。

## 3. 検証：早期チェックポイント問題を切り分ける

### 3-1. 実務タスクより軽い、最小構成での再現

実務タスク（CPD監査）は複雑すぎて、何が原因かの切り分けが困難です。そこで、`sleep 25 && echo RESULT_VALUE_IS_<乱数>`というダミー処理だけを使い、同じ「コーディネーター→サブエージェント」という構造だけを取り出しました。

**条件A**：コーディネーターへの指示で、サブエージェントに「まず『待機中です』とだけ先に報告し、フォローアップの催促を待ってから本回答を出せ」と明示。実務タスクで起きた構造をそのまま再現する狙いです。

結果、サブエージェント自身は正しい値（3325）を算出し、その報告は最上位セッションの会話には直接届きました。しかしコーディネーターへ強制的に状態確認をしたところ——

> Current state: I launched the subagent, received its first status update ("I've started the command and am standing by for it to finish"), then sent it a follow-up message asking for the actual result... I have not yet received a reply.

やはり、コーディネーターは本回答を受け取れていませんでした。

### 3-2. 「先に報告するな」と明示しても防げるか

もし早期チェックポイント自体を防げれば、そもそも往復が発生せず、この問題を回避できるはずです。**条件B**では、サブエージェントへの指示を「コマンドが完了して本当の結果が出るまでは一切報告するな。最初で最後の報告に、最初から本回答を含めよ」に変更しました。

結果は——

> I've resumed the subagent since it stopped prematurely (after only ~6.6 seconds — before the 25-second sleep could finish) with a "standing by" style message instead of the real result.

25秒のコマンド完了を待たず、約6.6秒で早期の「待機中です」という報告が返ってきました。**明示的な指示があっても、早期チェックポイントの発生自体は防げませんでした。** 結果、条件Aと同じ往復構造が発生し、その後の本回答もコーディネーターには届きませんでした。

### 3-3. 会話ではなく`TaskOutput`で直接取れないか

往復（`SendMessage`のやり取り）自体が不確実さの原因なら、会話を介さず、コーディネーターが自分で起動したタスクのIDに対して`TaskOutput(block: true)`を直接呼べば回避できるのではないか——**条件C**ではこれを試しました。

結果は、想定と違う理由で失敗しました。

> I attempted to use TaskOutput with block: true exactly as instructed, but that tool does not exist in this environment. I ran ToolSearch three times with different queries... none returned a TaskOutput tool.

**`TaskOutput`というツール自体が、コーディネーター役のサブエージェントの手元には存在しませんでした。** 実行時の失敗ではなく、ツール発見の時点での失敗です。これは、最上位セッションが持つツール一覧と、ネストされたサブエージェントが持つツール一覧が同一ではない、という副次的な発見でもあります。

## 4. 分かったこと

1. **2階層委譲での「二度目のやり取り」は、コーディネーターに届かないことがある。** 実務タスク1回＋軽量再現2回、合計3回、独立に同じ症状を確認しました。
2. **プロンプトの指示だけでは、サブエージェントの早期チェックポイントは防げません。** 「先に報告するな」と明示しても発生しました。
3. **想定した回避策（`TaskOutput`）も、少なくとも今回の環境では使えませんでした。** ネストされたサブエージェントは、セッション最上位と同じツール一覧を持つとは限りません。

一方で、良い発見もありました。コーディネーターは、報告を受け取れていない状況を、それらしい内容で埋め合わせることなく、正直に「不明」「捏造しない」と回答していました。存在しない情報を「大丈夫そうです」とそれらしく答えることもできたはずですが、しませんでした。委譲の配送経路には不具合がありましたが、コーディネーター自身の誠実さは保たれていた、という点は記録しておく価値があると思います。

## 5. Anthropic側の状況

新規にissueを立てる前に確認したところ、[anthropics/claude-code](https://github.com/anthropics/claude-code)側で、ほぼ同じ症状のissueが既に複数報告されていました。特に近いのが[#86996](https://github.com/anthropics/claude-code/issues/86996)「Subagent final assistant messages not delivered to parent session」で、内容はほぼ同じ症状（サブエージェントは完了・応答済みだが、親セッションには最終メッセージが届かない）です。他にも[#75043](https://github.com/anthropics/claude-code/issues/75043)、[#84527](https://github.com/anthropics/claude-code/issues/84527)、[#77908](https://github.com/anthropics/claude-code/issues/77908)、[#76945](https://github.com/anthropics/claude-code/issues/76945)など、関連する報告が複数存在します。

重複issueを新規に立てる代わりに、最も近い#86996へ、この再現結果——特に「カスタムフックが一切ない環境でも起きる」という点（#86996の報告者は`SubagentStop`/`SubagentStart`フックを主要な疑いとして挙げつつ「違うようだ」としていました）と、「先に報告するなと明示しても早期チェックポイントは防げない」という点——を、独立した追加証拠として[コメント投稿](https://github.com/anthropics/claude-code/issues/86996#issuecomment-5464266911)しました。

## 6. 本検証の限界

- 各検証は1回きりの試行です。統計的な再現率（何回に1回起きるか）は確認していません。
- コーディネーターとサブエージェントに固有の名前（`name`）を明示的に与えた場合に症状が変わるかは未検証です。今回使用した`Agent`ツールの呼び出しにはその項目自体がありませんでした。
- 内部の配送メカニズム（なぜ最上位セッションには届き、中間のコーディネーターには届かないのか）を直接見る手段がなく、観測された挙動からの推測にとどまります。

## 7. おわりに

今回の一連の作業は、実は「大量の項目をAIエージェントに監査させる」という別のタスク（[前回](https://zenn.dev/yuninaka/articles/delegated-audit-workflow)まとめたワークフロー）の実行中に、副産物として見つかったものでした。委譲したタスクの結果を鵜呑みにせず独立検証する、という姿勢を徹底していたからこそ、「コーディネーターが本当に報告を受け取れているか」という、本来なら見過ごしていたかもしれない疑問にたどり着けたのだと思います。

AIエージェントに複数階層の委譲を任せる設計は、今後ますます一般的になっていくはずです。委譲した先の報告が「静かに消える」ことがある、という前提を持っておくことは、少なくとも現時点では実務上必要な心構えだと感じています。
