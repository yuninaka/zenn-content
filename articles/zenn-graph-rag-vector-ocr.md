## 1. 概要

### 1.1 やったこと(3行サマリ)

- 前回記事([OCRの誤読をLLMが勝手に直した話——グラフRAGパイプライン完成編](https://zenn.dev/yuninaka/articles/zenn-graph-rag-pipeline-completion))で「今回はスコープ外」として残した、**ベクトルインデックス側のOCR由来データ対応**を実装した
- グラフ側と同じOCRノイズ(語の途中への空白混入)が、グラフ側とベクトル側で**まったく違う経路**を辿ることを実測した
- 前回発見した「LLMがOCRの誤読を正しく直してくれる」という現象には、**「同じ言葉に直すとは限らない」という見落としがあった**ことが今回分かった

リポジトリ: [graph-rag-maintenance-demo](https://github.com/yuninaka/graph-rag-maintenance-demo)
(この記事時点のコード: [`article-6-vector-ocr`タグ](https://github.com/yuninaka/graph-rag-maintenance-demo/tree/article-6-vector-ocr))

### 1.2 結果だけ先に

| データソース | graph | vector | 全体 |
|---|---|---|---|
| 合成データ直接使用 | 1.00 | 1.00 | 1.00 |
| **OCR由来データ**(グラフ・ベクトル両方) | **0.95** | **1.00** | **0.97** |

グラフ側だけ1件スコアが落ちた。原因はOCRのノイズそのものではなく、**そのノイズをLLMが「補正」した結果**にあった。

## 2. 前回までのおさらい:何が未接続だったか

前回記事で、「紙の書類(PDF)→OCR→ナレッジグラフ構築→ハイブリッド検索→回答」という一気通貫パイプラインを完成させた。しかしこれは`build_knowledge_graph.py`(グラフ構築)側だけの話で、`build_vector_index.py`(ベクトルインデックス構築)は合成データ固定のままだった。

```
[前回まで]
[PDF] → OCR → 変換層 → build_knowledge_graph.py → Neo4j(グラフ)
                          build_vector_index.py → Chroma(ベクトル) ← 未接続

[今回]
[PDF] → OCR → 変換層 → build_knowledge_graph.py → Neo4j(グラフ)
                          build_vector_index.py → Chroma(ベクトル) ← 接続
```

`build_knowledge_graph.py`は環境変数`MAINTENANCE_LOGS_PATH`でデータソースを差し替えられるようにしてあったので、同じパターンを`build_vector_index.py`にも適用した。あわせて、`hybrid_agent.py`が参照するChromaの永続化先も`CHROMA_PERSIST_DIR`で切り替えられるようにした。合成データ版のインデックス(`chroma_db/`)と混在させず、いつでも比較検証をやり直せるようにするためだ。

```python
# build_vector_index.py
DATA_PATH = Path(
    os.environ.get("MAINTENANCE_LOGS_PATH")
    or (Path(__file__).parent.parent / "data" / "maintenance_logs.jsonl")
)
PERSIST_DIR = Path(
    os.environ.get("CHROMA_PERSIST_DIR")
    or (Path(__file__).parent.parent / "chroma_db")
)
```

```bash
# OCR由来データでベクトルインデックスを構築
MAINTENANCE_LOGS_PATH=data/maintenance_logs_ocr.jsonl \
  CHROMA_PERSIST_DIR=chroma_db_ocr python -m src.build_vector_index
```

実装自体は既存パターンの再適用で、ここに特に難しさはなかった。面白かったのはこのあとの検証結果だ。

## 3. 検証:グラフ・ベクトル両方をOCR由来データで揃えて評価

Neo4jをOCR由来データで再構築し(前回記事と同じ手順)、ベクトルインデックスも上記コマンドでOCR由来データから構築したうえで、`evaluate.py`を実行した。

結果は冒頭の通り、graph 0.95・vector 1.00・全体0.97。vector型の4問はすべてscore=1.00を維持したが、graph型の5問中1問がscore=0.75に下がっていた。

## 4. 原因調査:「取り付けボルト」が「取付ボルト」に化けていた

score低下の犯人はQ5(「コンベアBが停止した原因を全て教えてください」)だった。期待キーワードには`取り付けボルト`が含まれているが、実際の回答には`取付ボルト`(送り仮名なし)としか出てこなかった。

まず元データを確認した。R005の原文はこうだ。

```
モーター取り付けボルトの緩みが判明。
```

送り仮名(り・け)込みで書かれている。ところがOCR結果を見ると、単語の途中に余計な空白が挿入されていた。

```
モーター取り付けボ ルトの緩みが判明。
```

このノイズ入りのテキストを`build_knowledge_graph.py`のLLM抽出に通した結果、`cause`フィールドはこう出力された。

```python
{'cause': 'モーター取付ボルトの緩み', ...}
```

**「取り付けボ ルト」という壊れた文字列が、「取付ボルト」という別の(でも間違ってはいない)表記に書き換わっていた。**

これは前回記事のR012(「〇リング」→「Oリング」)と同じ「LLMがOCRのノイズを文脈から補正した」現象ではある。しかし前回とは決定的に違う点がある。R012の場合、補正後の表記(`Oリング`)は元の正解データの表記と完全に一致していた。今回のケースでは、補正後の表記(`取付ボルト`)は**元の正解データの表記(`取り付けボルト`)とは異なる、しかし意味的には同じ別の日本語表記**になっている。

なぜLLMがこの表記を選んだのかも、データを見ると推測できる。同じ設備(コンベアB)の別の報告書R017の本文に、こういう記述がある。

```
前回(R005)は取付ボルトの緩み、前々回(R008)はモーターのコイル絶縁不良が原因だったが...
```

R017自身が、R005を振り返る際に送り仮名なしの「取付ボルト」という表記を使っている。LLMが壊れたR005のテキストを補完する際、こうした一般的な表記ゆれの中から、たまたま送り仮名なしの形を選んだのだろう。どちらの表記も日本語として正しく、意味も同じだが、`golden_qa.jsonl`のキーワード部分一致評価はこの表記ゆれを区別してしまう。

## 5. ベクトル側はなぜ影響を受けなかったのか

同じOCRノイズ(「取り付けボ ルト」)は、ベクトル側のインデックスにも当然含まれている。実際にChromaに格納された内容を直接確認した[^1]。

```python
vs = Chroma(persist_directory='chroma_db_ocr', embedding_function=embeddings)
res = vs.get(where={'report_id': 'R005'})
print(res['documents'][0])
# 'コンベアBのモーターから異音および振動を確認。原因調査の結果、
#  モーター取り付けボ ルトの緩みが判明。...'
```

グラフ側と違い、ベクトル側にはLLMによる書き換えの工程が存在しない。`build_vector_index.py`は本文をそのままチャンク化して埋め込みモデルに渡すだけなので、**OCRのノイズはそのまま埋め込みベクトルに反映される**。それでも今回、vector型の4問はすべてscore=1.00を維持した。多言語埋め込みモデル(intfloat/multilingual-e5-small)の意味的類似度計算が、単語途中への半角スペース1つ程度のノイズに対しては十分頑健だったということだろう。

つまり今回の実測で分かったのは、こういう構図だ。

| | ノイズへの対応 | 今回の結果 |
|---|---|---|
| グラフ側(LLM抽出を経由) | 補正するが、**元の表記と一致する保証はない** | 表記が変わり、キーワード評価で減点 |
| ベクトル側(生テキストを埋め込み) | 補正せず、ノイズをそのまま保持 | 埋め込みの頑健性で吸収され、無影響 |

「LLMが賢く補正してくれるから安心」という前回記事の結論は、半分正しく半分足りなかった。**補正されること自体は起きるが、補正後の表記が元の表記と一致するとは限らない**という一段深い注意点が、ベクトル側と比較して初めて見えてきた。

## 6. 得られた知見

### 6.1 「LLMが誤読を直す」は「元の表記に戻す」とは限らない

前回記事の結論(OCRの誤読はLLM抽出段階で自然に補正される)は、R012の1件だけを見ていた段階では正しく見えた。しかし今回のR005のケースでは、補正は起きたものの、結果として生まれた表記は元のテキストとは異なる**別の正しい表記**だった。「LLMが直してくれるから、OCRの精度は気にしなくていい」という考え方には、今回さらに踏み込んだ注意が必要だと分かった。表記が変わっても意味が保たれていれば実用上は問題ないことが多いが、**完全一致や部分一致に依存する評価・検索の仕組みにとっては、これは無視できない差**になる。

### 6.2 グラフとベクトルでは、同じノイズでも伝播経路が違う

同じOCR結果を入力にしても、グラフ側は抽出という「解釈」の工程を通るため表記が変わりうるのに対し、ベクトル側は生テキストをそのまま埋め込むため表記は変わらない(その代わり、埋め込みモデル自体の頑健性に精度が依存する)。今回はたまたまベクトル側の頑健性がノイズを吸収したが、これは「ベクトル側は常に安全」という意味ではない。もっと大きな崩れ方をするOCRノイズであれば、埋め込みの類似度計算も影響を受けるはずだ。パイプラインのどの段階にどんな種類の頑健性があるかを、実際に両方の経路を動かして比較しないと分からない、ということを改めて実感した。

### 6.3 golden_qaのキーワード部分一致評価の限界が、また1つ見つかった

第2弾記事でも、golden_qaのキーワード評価が「回答の過不足」を検知できないケースを見つけた。今回は「意味は同じだが表記が異なる」場合に減点されるという、また別の限界が見つかった。今回はこのキーワード自体は修正せず、**評価方法自体の限界の実例**として記録するに留めた。表記ゆれを許容する評価(類似度ベースの評価など)に切り替える選択肢もあるが、その場合は逆に「意味は違うが表記が近い」誤答を見逃すリスクとのトレードオフになる。

## 7. まとめと今後

前回記事で残した「ベクトルインデックス側のOCR対応」を実装し、グラフ側とベクトル側でOCRノイズの伝播経路がどう違うかを実測できた。前回の「LLMが誤読を直してくれる」という発見は、今回「直った先の表記が元と一致する保証はない」という、もう一段深い知見に更新された。

残っている課題は次の2つ。

1. **本物のスキャン/写真での検証**: 今回もデジタルネイティブPDFでの検証にとどまっている。紙に印刷してスキャンした画像や手書き文字を含む書類では、もっと大きな崩れ方をするノイズが発生するはずで、そのときグラフ側・ベクトル側それぞれがどこまで頑健かは未検証
2. **評価方法自体の見直し**: golden_qaのキーワード部分一致という評価方法は、今回のような表記ゆれや、第2弾で見つけた過不足の検知漏れなど、複数の限界が積み上がってきている。より頑健な評価方法(類似度ベースの評価等)への切り替えを検討する価値がある

次回はこのいずれか、あるいは合成データの拡張に進みたい。

[^1]: `hybrid_agent.py`が使うのと同じ`langchain_community.vectorstores.Chroma`クラスで、実際に永続化されたベクトルストア(`chroma_db_ocr/`)を直接開き、`vs.get(where={"report_id": "R005"})`でメタデータフィルタして格納済みのチャンク本文(`page_content`)を取得している。LLMの回答やAgentの出力を経由せず、ディスク上の実データを直接見る形の確認方法。
