## 1. 概要

### 1.1 やったこと(3行サマリ)

- 設備保全ドメイン(操業日誌・トラブル報告書)を模した合成ログ35件から、ベクトルRAG(Chroma)とナレッジグラフ(Neo4j AuraDB Free)を構築した
- LangChainのAgentに `vector_search` と `graph_query`(GraphCypherQAChain)の2ツールを持たせ、質問内容に応じて自律的に使い分けるハイブリッドRAGエージェントを実装した
- 9問のゴールデンQAでキーワード網羅率による精度評価を行い、スコアが低かった質問を実データまで遡って原因分析した

リポジトリ: [graph-rag-maintenance-demo](https://github.com/yuninaka/graph-rag-maintenance-demo)
(この記事時点のコード: [`article-1-limitations`タグ](https://github.com/yuninaka/graph-rag-maintenance-demo/tree/article-1-limitations)。`main`はその後の記事で更新され続けています)

### 1.2 結果だけ先に:全体精度0.89、ただしvectorとgraphで明暗が分かれた

| type別 | 平均スコア | 件数 |
|---|---|---|
| vector | **1.00** | 4件 |
| graph | **0.80** | 5件 |
| 全体 | **0.89** | 9件 |

vector検索(類似文書検索)は全問満点だった一方、graph検索(自然言語→Cypher変換によるナレッジグラフ探索)は1問(0.00)が足を引っ張り、平均0.80止まりだった。

グラフRAGは「集計・因果関係を辿る質問」に強いはずだと思って設計したが、実際にボトルネックになったのは検索方式そのものではなく、**ナレッジグラフのノード設計(表記ゆれ・名寄せの有無)** だった。この記事は、その「うまくいかなかった部分」を含めて記録したものです。

## 2. なぜこの技術検証をしたか

### 2.1 生成AI市場の変化(実験期→実利追求期)

LLMを使ってとりあえず何かを動かしてみる「実験期」から、実務でどこまで精度・コストを詰められるかが問われる「実利追求期」に移りつつある。単発のチャットボットではなく、社内データを構造化して検索可能にする(ナレッジグラフ化・ベクトル化)案件が増えており、「動くものを作れる」だけでなく「なぜその精度なのか、なぜその設計なのか」を自分の言葉で説明できる経験が求められると感じている。

### 2.2 検証テーマにベクトルRAG/グラフDBを選んだ理由

求人票でよく見る必須/歓迎スキルと、このプロジェクトの対応箇所を最初にマッピングした。

| 求人の必須/歓迎スキル | 本プロジェクトでの対応箇所 |
|---|---|
| ナレッジグラフのデータ構造(ノード・エッジ)設計 | `docs/schema.md`、`build_knowledge_graph.py` |
| AI-OCRで構造化したデータのグラフ化(Python) | 構造化済み合成データ + `build_knowledge_graph.py`(拡張ポイントを明示) |
| グラフDB(Neo4j等OSS)へのデータ投入・運用 | `build_knowledge_graph.py`(Neo4j AuraDB Free) |
| LangChain/LangGraphでのAIエージェント | `hybrid_agent.py` |
| 想定通りの回答が得られない場合の原因分析 | `docs/troubleshooting_log.md` |
| 回答精度の測定方法の設計・評価 | `evaluate.py` + `golden_qa.jsonl` |
| ベクトルRAG(チャンク設計・インデックス設計) | `build_vector_index.py` |

ベクトルRAG単体の検証記事は世の中に多いが、「集計・因果関係を辿る質問にはグラフDBを組み合わせる」という一歩踏み込んだ構成を、実際に手を動かして検証した。

## 3. アーキテクチャ設計

### 3.1 全体構成図

```
[非構造化ログ(合成データ35件)]
        │
        ├─→ [チャンク分割 + 埋め込み] → [Chroma(ベクトルDB)] ──┐
        │                                                      │
        └─→ [LLMによるエンティティ/関係抽出] → [Neo4j(グラフDB)]─┤
                                                                 ▼
                                                    [LangChain ハイブリッド検索]
                                                    ・ベクトル類似検索 Retriever
                                                    ・GraphCypherQAChain
                                                                 │
                                                                 ▼
                                                   [Agent: 質問に応じてツール選択]
                                                                 │
                                                                 ▼
                                                        [回答 + 精度評価]
```

### 3.2 なぜベクトル検索とグラフ検索を両方使うのか

- **ベクトル検索が得意なこと**: 「〇〇のような症状が出た場合、考えられる原因は?」のような、自然文の類似検索。過去の報告書の"雰囲気"が近いものを引っ張ってくるのに強い
- **グラフ検索が得意なはずのこと**: 「過去に何回発生したか」「最も多い原因は何か」のような、集計・因果関係を辿る質問。ベクトル検索はチャンク単位の類似度計算しかできないため、こうした構造的な集計は原理的に苦手

この住み分けを検証するために、9問のゴールデンQAを意図的に vector向き/graph向きで分けて用意した(後述)。

### 3.3 得意・不得意の対比表(vector vs graph)

| 観点 | vector検索 | graph検索(text-to-Cypher) |
|---|---|---|
| 類似文書の想起 | ◎ 埋め込み距離で自然に近似できる | △ 完全一致/CONTAINS前提だと表記ゆれに弱い |
| 集計(件数・頻度) | × チャンクを数えても意味を持たない | ◎ Cypherの`count()`で正確に集計できる...**はずが、名寄せ不足だと×** |
| 因果関係の多段階の追跡 | × 文書内の記述に依存 | ◎ `CAUSED_BY`→`RESOLVED_BY`のようなエッジを辿れる |
| 未知の言い回しへの頑健性 | ◎ 意味的に近ければヒットする | × ノード名の文字列一致に強く依存する |
| 実装・運用コスト | 埋め込みモデルさえあれば安価 | スキーマ設計・抽出精度・Cypher生成の3点に依存 |

理屈の上ではこの表の通りだが、実測してみると「graphの◎」は**ノード設計の質が伴って初めて成立する**ということが、今回の一番の学びだった(6章・7章で詳述)。

## 4. ナレッジグラフのスキーマ設計

### 4.1 ノード/エッジ設計

| ノードラベル | 説明 |
|---|---|
| `Equipment` | 設備・機器(例: コンベアA、ポンプ3号機) |
| `Symptom` | 発生した症状・現象(例: 異音、過熱、停止) |
| `Cause` | 原因(例: ベアリング摩耗、潤滑不足) |
| `Action` | 対処・修理内容(例: ベアリング交換、注油) |
| `Part` | 使用部品(例: ベアリング型番6205) |
| `ReportEvent` | 個々の報告書・日誌エントリ |

| 関係 | From → To | 意味 |
|---|---|---|
| `OCCURRED_ON` | ReportEvent → Equipment | どの設備の報告か |
| `HAS_SYMPTOM` | ReportEvent → Symptom | どんな症状が報告されたか |
| `CAUSED_BY` | Symptom → Cause | 症状の原因 |
| `RESOLVED_BY` | Cause → Action | 原因への対処方法 |
| `USES_PART` | Action → Part | 対処に使った部品 |

### 4.2 Symptom→Cause→Actionの因果チェーンを蓄積する設計思想

`Symptom`ノードを名前でMERGEすることで、複数の`ReportEvent`(=複数回のトラブル)が同じ`Symptom`ノードに集約され、そこから複数の`Cause`が枝分かれする形でグラフに蓄積されていく。これにより「同じ症状が過去に何度発生し、それぞれ何が原因でどう解決されたか」をCypher1本で辿れるようにする、というのが設計の狙いだった。

### 4.3 実データでの枝分かれ例(ポンプ3号機:同一症状・3原因のケース)

実際にこの狙い通りの構造ができたのが、ポンプ3号機の「吐出圧力低下」症状だった。

```cypher
MATCH (e:Equipment {name: "ポンプ3号機"})<-[:OCCURRED_ON]-(r:ReportEvent)
      -[:HAS_SYMPTOM]->(s:Symptom)-[:CAUSED_BY]->(c:Cause)
RETURN r.report_id, s.name, c.name
```

| 報告書 | 症状 | 原因 |
|---|---|---|
| R002 | 吐出圧力低下 | 羽根車への異物噛み込み |
| R007 | 吐出圧力の低下 | 吸込配管のフィルター目詰まり |
| R015 | 吐出圧力の低下 | 軸封部(メカニカルシール)の摩耗による内部漏れ |
| R035 | 吐出圧力の低下 | (過去4回の再発を受け)設計上の余裕不足を疑い、上位機種への更新を提案 |

同一設備・同一症状なのに、原因は毎回異なっている。これはグラフRAGでなければ拾いにくい「繰り返し発生しているが原因が毎回違う」というパターンで、R035では過去の再発履歴を踏まえて「対症療法ではなく設計自体を見直すべきでは」という一段深い提案に繋がっている。この"因果チェーンの蓄積が根本原因の疑いに繋がる"という流れこそがグラフRAGを入れる価値だと感じた一方、この例がうまくいったのは症状名の表記(「吐出圧力低下」「吐出圧力の低下」)がたまたま近かったから、という側面もある(7章で詳述)。

## 5. 実装

### 5.1 ベクトルRAG: チャンク設計の判断根拠

今回の合成データは1レポートあたり数百字程度で十分短いため、基本的には「レポート単位=チャンク単位」とした。`RecursiveCharacterTextSplitter(chunk_size=400, chunk_overlap=50)` は保険として入れているが、実際にはほぼ分割されない。実案件でより長い文書(仕様書・図面添付テキスト等)を扱う場合はオーバーラップ付き分割が必須になる、という拡張ポイントをコードコメントで明示した。

埋め込みモデルはAPI課金を避けるため、ローカルで動く多言語モデル `intfloat/multilingual-e5-small` を採用。日本語の意味検索にも対応できる。

### 5.2 グラフDB: エンティティ抽出とNeo4jへの投入

報告書テキストから `{equipment, symptom, cause, action, part}` のJSONをLLMに抽出させ、以下のCypherで`MERGE`ベースにUpsertする。

```cypher
MERGE (eq:Equipment {name: $equipment})
MERGE (r:ReportEvent {report_id: $report_id})
  SET r.date = $date, r.reporter = $reporter
MERGE (r)-[:OCCURRED_ON]->(eq)
MERGE (s:Symptom {name: $symptom})
MERGE (r)-[:HAS_SYMPTOM]->(s)
MERGE (c:Cause {name: $cause})
MERGE (s)-[:CAUSED_BY]->(c)
MERGE (a:Action {name: $action})
MERGE (c)-[:RESOLVED_BY]->(a)
```

`MERGE`はキーが一致すれば既存ノードを再利用するため、同じ設備名・同じ症状名であれば自動的にノードが統合される。裏を返すと、**文字列が1文字でも違えば別ノードとして分裂する**という性質でもあり、これが後述の不具合の元になった。

### 5.3 コスト設計: Claude Code定額とAPI課金の使い分け

#### バッチ抽出処理→`claude -p`(Pro/Max定額)に寄せた判断

35件のエンティティ抽出は「1件ずつの単発呼び出しで完結するバッチ処理」であり、LangChainのTool-calling(Function calling)プロトコルを必要としない。そこで `claude -p "<プロンプト>"` をPythonの`subprocess`から呼び出す方式にし、Claude Pro/Maxプランの定額枠内で完結させた。

#### LangChain Agent検証部分のみAPI課金を許容した理由

一方 `hybrid_agent.py` のLangChain Agentは、API側のFunction calling機構そのものを検証する部分であり、ここをClaude Codeに置き換えるとLangChain Agent実装の検証という本来の目的から外れる。そのため少額のAPI課金を許容し、Anthropic APIを直接叩く実装にしている。

#### 実装時に見つけた「サブスクとAPIの二重課金」落とし穴と対策

実装中、`build_knowledge_graph.py`(`claude -p`経由でPro/Max定額のはず)を実行したところ、以下のエラーで失敗した。

```
⚠ claude.ai connectors are disabled because ANTHROPIC_API_KEY or another
  auth source is set and takes precedence over your claude.ai login
Invalid API key · Fix external API key
```

原因は、`.env`に(まだ使っていない)`ANTHROPIC_API_KEY`を設定していたこと。Pythonの`load_dotenv()`がこの値をプロセス環境変数として読み込み、`subprocess.run(["claude", "-p", ...])` がその環境変数を継承してしまう。`claude` CLIは **claude.aiログイン(Pro/Max)より環境変数`ANTHROPIC_API_KEY`を優先する仕様** のため、無効なダミー値では素通しどころかエラーで停止した。

これは裏を返すと、**もしダミー値ではなく本物の有効なAPIキーを`.env`に置いていたら、「Pro/Maxの定額枠で回っているつもり」で実は毎回API課金されていた**ことになる。コスト設計上、致命的な見落としになりかねないポイントだった。

対策として、`claude`をサブプロセス実行する際は`ANTHROPIC_API_KEY`を環境から明示的に除外するようにした。

```python
# ANTHROPIC_API_KEY(.envのダミー値含む)が環境にあると、claude CLIが
# claude.aiログイン(Pro/Max定額)より優先してそれを使おうとし失敗するため除外する
env = {k: v for k, v in os.environ.items() if k != "ANTHROPIC_API_KEY"}
result = subprocess.run(["claude", "-p", prompt], capture_output=True, text=True, timeout=60, env=env)
```

「サブスク定額のつもりで実装したバッチ処理に、いつのまにかAPIキーが割り込んでいないか」は、Claude Code CLIとLangChain(API)を併用する構成では必ずチェックすべき項目だと感じた。

### 5.4 ハイブリッドエージェント: LangChainのRetriever + GraphCypherQAChain

`vector_search`(Retriever)と`graph_query`(`GraphCypherQAChain`: 自然言語→Cypher変換→実行→自然言語回答)の2つをツールとして持たせ、Agent自身にどちらを使うか判断させる構成にした。

実装中、LangChainのメジャーバージョンアップ(1.x系)でAgent構築APIが刷新されていたことに気づかず、しばらくハマった。

```python
# 旧API(LangChain 0.x系): 廃止済み
from langchain.agents import AgentExecutor, create_tool_calling_agent
agent = create_tool_calling_agent(llm, tools, prompt)
executor = AgentExecutor(agent=agent, tools=tools)
result = executor.invoke({"input": query})["output"]

# 新API(LangChain 1.x系): LangGraphベースに刷新
from langchain.agents import create_agent
agent = create_agent(llm, tools, system_prompt="...")
result = agent.invoke({"messages": [{"role": "user", "content": query}]})
answer = result["messages"][-1].content
```

`requirements.txt`にバージョン下限(`langchain>=0.3.0`)しか書いていなかったため、pipが最新の1.x系を入れてこの非互換に直面した形。ライブラリのメジャーバージョン更新が早いLangChainでは、`>=`だけのバージョン指定はサンプルコードの寿命を縮めるリスクがあると実感した。

## 6. 精度評価

### 6.1 評価方法の設計(golden_qa 9問、キーワード網羅率という手法とその限界)

`golden_qa.jsonl`に、想定回答に含まれるべきキーワード群を人手で定義し、Agentの実際の回答にキーワードが何割含まれるかでスコアリングする「キーワード網羅率」方式を採用した。

```python
def keyword_coverage(answer: str, keywords: list[str]) -> float:
    hit = sum(1 for kw in keywords if kw in answer)
    return hit / len(keywords) if keywords else 0.0
```

LLM-as-judge(別のLLMに正誤判定させる)より安価・再現性が高い一方、**表現の言い換えを拾えない**弱点がある(例えば「メカニカルシール」を「軸封部のシール」と言い換えられるとキーワード一致しない)。今回は9問という小規模な評価だったため、期待キーワードを絞って厳密性を担保する運用でカバーした。

### 6.2 結果:全体0.89 / vector 1.00(4件) / graph 0.80(5件)

| ID | type | スコア | 質問 |
|---|---|---|---|
| Q1 | graph | 0.00 | コンベアAでベアリングの異音は過去に何回報告されていますか? |
| Q2 | graph | 1.00 | ポンプ3号機の吐出圧力低下の原因として過去にあったものを教えてください |
| Q3 | vector | 1.00 | コンベアAのベルトから異音がする場合、考えられる原因は何ですか? |
| Q4 | vector | 1.00 | ポンプ3号機の軸受け発熱の対処法として何が行われましたか? |
| Q5 | graph | 1.00 | コンベアBが停止した原因を全て教えてください |
| Q6 | graph | 1.00 | 空調ユニット1号機で過去に発生したトラブルを全て教えてください |
| Q7 | vector | 1.00 | 搬送ロボット1号機のアーム異常の原因として考えられるものは何ですか? |
| Q8 | vector | 1.00 | 圧縮機Aの吐出温度上昇の原因は何でしたか? |
| Q9 | graph | 1.00 | ポンプ3号機で吐出圧力低下が発生した原因は何回、それぞれ何が原因でしたか? |

実はこの数字にたどり着くまでに、2回の修正を挟んでいる。

| 段階 | graph平均 | vector平均 | 全体 |
|---|---|---|---|
| 初回実行 | 0.58 | 1.00 | 0.77 |
| ①Equipmentノードの名寄せ修正後 | 0.75 | 1.00 | 0.86 |

①は「コンベアB」がLLM抽出の自由記述により「コンベアBのモーター」「コンベアB ベルト駆動プーリー」の3ノードに分裂していた不具合(詳細は8.2)。②は評価データ側の誤り(Q5の期待キーワード「詰まり」が、実は報告書本文で「詰まりは**見当たらず**」と否定形で言及されていただけで、実際の原因ではなかった)を、報告書原文まで遡って修正したもの。

### 6.3 vectorが強くgraphが弱かったことの考察

3.3節の対比表通りなら、「過去に何回」「原因を全て」のような集計質問(graph向き)は本来graphの得意分野のはずだった。実際に低スコアだった原因は、text-to-Cypherの生成精度そのものよりも、**その前段のノード設計(名寄せ)の甘さ**にあった。埋め込みベクトルは"意味が近ければ多少の表記ゆれを吸収できる"のに対し、Cypherの`MATCH {name: "..."}`や`CONTAINS`は基本的に文字列ベースの一致判定であり、表記ゆれに弱い。「グラフDBは構造化されているから精度が高い」という思い込みは正しくなく、**構造化の質(=スキーマ設計とエンティティ正規化)が伴わなければ、むしろベクトル検索より脆い**ということを、実測を通じて学んだ。

## 7. うまくいかなかった点の深掘り:Q1(0.00)の原因分析

### 7.1 何を聞いて、何が返ってきたか

質問: 「コンベアAでベアリングの異音は過去に何回報告されていますか?」
期待キーワード: `3`, `R001`, `R006`, `R010`(実際にコンベアAでベアリング関連の異音を報告した3件)

Agentが生成したCypher:

```cypher
MATCH (r:ReportEvent)-[:OCCURRED_ON]->(e:Equipment {name: 'コンベアA'})
MATCH (r)-[:HAS_SYMPTOM]->(s:Symptom)
WHERE s.name CONTAINS 'ベアリング' AND s.name CONTAINS '異音'
RETURN count(r) AS occurrence_count
```

結果は `occurrence_count: 1`。回答は「過去に1回報告されています」となり、期待した3件から大きく外れてスコア0.00となった。

### 7.2 原因:Symptomノードが自由記述のまま名寄せされていない

該当する3件のSymptomノードの実際の値を確認すると、以下のようにすべて別の文字列だった。

| 報告書 | Symptomノードの値 |
|---|---|
| R001 | 搬送ベルトの異音・ローラー部のガタつき |
| R006 | ベルトの異音 |
| R010 | ベアリングからの異音 |

生成されたCypherは`CONTAINS 'ベアリング' AND CONTAINS '異音'`というAND条件だったため、両方の単語を含むR010だけがヒットし、R001・R006は"意味的には関連するが文字列としては一致しない"という理由で漏れた。

### 7.3 「同じ症状でも表記が違うと別ノード扱いになる」設計上の課題

これは4.2節で書いた「`MERGE`によるノード統合」の裏側の弱点そのものだった。LLMによる自由記述抽出は、同じ現象でも呼び方が毎回微妙に揺れる(「ベルトの異音」「ベアリングからの異音」「搬送ベルトの異音・ローラー部のガタつき」)。`MERGE`は完全一致でしかノードを統合しないため、これらは別々のSymptomノードとしてグラフに蓄積されてしまう。text-to-Cypherがどれだけ賢くても、探索対象のグラフ自体が細かく分裂していれば正しい集計はできない。

なお、似た構造の問題は6.2節で触れたEquipmentノードの分裂(「コンベアB」が3ノードに分裂)としても実際に発生していた。こちらは「LLMの自由記述抽出結果ではなく、元データの正規化済みフィールドを常に使う」という比較的簡単な修正で解決できた(8.2節)。一方、Symptomの表記ゆれは「そもそも構造化された正解データが存在しない自由記述テキストの正規化」であり、同じ"名寄せ"問題でも解決の難易度が異なる。

### 7.4 根本対応案(カテゴリ/タグ付けの導入)と、あえて未着手のまま公開した理由

根本対応としては、Symptom抽出時にLLMへ「あらかじめ定義したカテゴリ一覧から選ばせる」「自由記述の症状文とは別に正規化タグ(`category`プロパティ)を持たせる」といったスキーマ拡張が必要になる。あるいはCypher生成側で完全一致ではなくベクトル類似度ベースのファジーマッチ(Neo4jのベクトルインデックス機能等)を組み合わせる方法もある。

今回はこの対応を意図的に未実装のまま`docs/troubleshooting_log.md`に記録して公開した。理由は2つある。1つは、この問題が「実装ミス」ではなく「LLM抽出ベースのグラフRAGに構造的に付きまとう設計課題」であり、"どう気づいて、どう記録したか"自体に価値があると考えたため。もう1つは、Equipmentノードの分裂(簡単に直せる問題)とSymptomノードの表記ゆれ(設計拡張が必要な問題)を混同せず、対応の優先順位・難易度を切り分けて示す方が、原因分析の練習として誠実だと考えたためです。

## 8. 得られた知見

### 8.1 ベクトル検索とグラフ検索、使い分けの判断軸(実測ベースで再整理)

- 「類似する過去事例を自然文で探したい」→ vector検索。表記ゆれに強く、実装コストも低い
- 「正確な集計・因果関係を辿りたい」→ graph検索。ただし**エンティティ正規化(名寄せ)が伴わない限り、期待した精度は出ない**
- 実務では「graphに寄せれば集計は安心」ではなく、「graphを使うならエンティティ正規化にコストを割く覚悟ができるか」がまず問われる

### 8.2 グラフRAGの精度は「スキーマ設計の質」に直結する、という発見

`docs/schema.md`を書いた時点では、ノード・エッジの型(`Equipment`/`Symptom`/`Cause`...)さえ決めれば設計は完了だと考えていた。しかし実際には、ノードの**プロパティ値(name)の正規化ルール**まで設計に含めない限り、`MERGE`ベースのグラフ構築は簡単に破綻する。

今回見つかった2つの分裂パターンはどちらもこれが原因だった。

- Equipmentノードの分裂: `build_knowledge_graph.py`が`claude_code`抽出モードのとき、元データの正規化済み`record["equipment"]`(例:「コンベアB」)ではなく、LLMが本文から自由記述抽出した設備名(「コンベアBのモーター」「コンベアB ベルト駆動プーリー」)をそのまま使っていたのが原因。`rule_based`モードだけ元データで上書きする処理があったが、`claude_code`モードには同様の処理が漏れていた。すべての抽出方式で `equipment=record["equipment"]` を常に使うよう修正し、Neo4jを再構築したところEquipmentノードが正しく8設備・8ノードに統合された(6.2節の①)。
- Symptomノードの分裂: 7章で詳述した通り、こちらは元データ側に正規化済みフィールドが存在しない(自由記述のみ)ため、Equipmentのような単純な上書きでは直せなかった。

「構造化されたグラフだから精度が出る」のではなく、「構造化の過程(抽出・正規化)にどれだけ設計とコストを割けたか」が精度に直結する、というのが最大の発見だった。

### 8.3 AIエージェントに委ねてよい範囲/人間の検証が必須な範囲

今回の検証を通じて感じた境界線は以下の通り。

- **委ねてよかった範囲**: 定義済みJSONスキーマに沿ったエンティティ抽出、vector/graphのツール選択(Agentの自律判断)、Cypherの生成そのもの(質問文からのtext-to-Cypher変換の精度自体は高かった)
- **人間の検証が必須だった範囲**: 抽出されたエンティティが「同じ実体を指しているか」の判断(名寄せ)、低スコアの原因が実装バグなのか評価データ側の誤りなのかの切り分け(6.2節②のgolden_qa修正は、報告書原文を人間が読み直して初めて気づけた)、根本対応を今すぐやるか・課題として記録するにとどめるかの優先順位判断

特に「golden_qa.jsonl側の期待値が間違っていた」ケースは、Agentの回答をそのまま信じていたら気づけなかった。低スコアが出たときに「実装のバグ」を疑うのと同じ熱量で「評価データ自体が正しいか」も疑う必要がある、というのは前回までの検証でも繰り返し痛感してきた点だが、グラフRAGという新しい題材でも同じ教訓が再確認できた。
