## 1. はじめに

[前回](https://zenn.dev/yuninaka/articles/legacy-ai-type-guardrails)・[前々回](https://zenn.dev/yuninaka/articles/legacy-ai-test-gen)の記事では、レガシーJavaライブラリを題材に、AIエージェントへ「CIの全ゲートがPASSするまで自律的に繰り返せ」という指示を何度も投げてきました。この形式——エージェントが「変更する→検証する→失敗したら直す」というループを、人間の介入なしに何十周も自律的に回す構成——は Agentic Loop（あるいは ReAct パターン）と呼ばれ、複雑なタスクを高い柔軟性で解決できる一方、構造的なリスクも抱えています。

その一つが**トークン爆発**です。多くのAgentic Loop実装は、各ターンでそれまでの会話履歴全体を再送信します。ループが長引くほど1ターンあたりの処理量が増え、コストとレイテンシが悪化し、さらにコンテキストが溢れると「指示忘れ（Lost in the Middle）」による精度低下まで起こり得ます。

静的ガードレール——コンパイラ、型チェッカー、静的解析、決定論的なCIスクリプトなど、LLMの「気分」に依存しない機械的な合否判定——は、本来[前回記事](https://zenn.dev/yuninaka/articles/legacy-ai-type-guardrails)で見たとおり、**コードの品質・正しさを担保するための仕組み**です。実際、このセッションで使ってきた`./scripts/ci-harness.sh`も、その目的で導入されたものでした。

この品質担保の仕組みが、Agentic Loop特有の別の問題であるトークン爆発まで副次的に抑えてくれるのではないか——という期待を持つ読者もいるかもしれません。しかし「静的ガードレールがあればトークン爆発を防げる」という主張は、そのままでは検証されていない仮説です。本記事では、実際に小規模な対照実験を行い、さらにこのセッション自体で発生した大規模タスクの生ログを解析することで、この仮説がどこまで正しく、どこが単純化しすぎだったかを検証します。

## 2. ループエンジニアリング（Agentic Loop）の光と影

**メリット**：高い柔軟性と、自律的に複雑なタスクを解決する力。人間が逐一手順を指示しなくても、「目標」と「合否判定手段」さえ与えれば、試行錯誤しながら収束させられます。

**デメリット（構造的リスク）**：

- **無限ループ・思考の停滞**：明確な終了条件がないと、いつまでも同じ場所を回り続けたり、途中で収拾がつかなくなったまま止まったりします。実際このセッションでも、大規模な静的解析ガードレール構築タスクの1回目の実行で、661ターンのうち556ターン目付近でエージェントの報告が断片的になり（「Confirmed final, no subclasses.」）、これを見た私が未完了と判断して再開の指示を送りました。何が原因でそうなったのか——エージェント自身のリソース制約なのか、それとも他の要因なのか——は、後からログを調べても断定できませんでした。ただ、**有限のはずのタスクが、規模の大きさゆえに一度で収まらなかった**という事実自体は、規模が大きくなるほど現実的に起こりうる失敗モードとして残ります。
- **トークン爆発**：会話履歴を毎ターン再送信する構成では、大きな固定コンテキスト（システムプロンプト・ツール定義・タスク指示）を毎ターン律儀に送り直すコストと、会話が進むにつれて履歴が積み上がっていく成長分のコストが両方効いてきます。**タスク全体で実際に処理される総トークン量は、単純な線形増加をはるかに超えて膨らみます**（内訳の詳細は次章の実測データで示します）。
- **コンテキスト溢れによる精度低下**：文脈が肥大化すると、初期の指示や制約がコンテキストの中盤に埋もれ、LLMがそれを見落とす（Lost in the Middle）リスクが高まります。

## 3.【検証データ】静的ガードレールの有無で何が変わるか

### 3-1. 小規模な対照実験

同一の「意図的にバグを仕込んだ小さなJavaユーティリティクラス」を用意し、以下の条件を揃えて2つの新規エージェント（互いの存在を知らない、このセッションの文脈も引き継がない）に並列で修正させました。

- **ケースA（LLM自己判断）**：自動テストなし。「Javadocの契約と一致するよう直せ」とだけ指示し、完了判断はエージェント自身に委ねる。
- **ケースB（静的ガードレール）**：あらかじめ用意したテストスイート（`mvn test`）を与え、「全テストがPASSするまで自律的に繰り返せ」と明示的に指示する。

バグの内訳は、コンパイルエラー1件（代入演算子の誤用）、命名規約違反1件、ロジックバグ3件（配列の最後の出現位置を返すべきが最初を返す／連続する空白の扱いが誤り／整数除算による精度落ち）です。

| 指標 | ケースA（LLM自己判断） | ケースB（静的ガードレール） |
| :--- | :--- | :--- |
| トークン消費量 | 47,757 | 47,014 |
| ツール呼び出し回数 | 23回 | 18回 |
| 所要時間 | 約5分13秒 | 約3分43秒 |
| 隠しテスト（10件、両者とも未提示）の結果 | 10/10 PASS | 10/10 PASS |

**想定外だった点**：トークン消費量の差はわずか1.6%で、ほぼ誤差でした。「静的ガードレールがないとトークンが爆発する」という単純な仮説は、この小規模・単一ファイルのタスクでは裏付けられませんでした。差が明確に出たのはツール呼び出し回数（28%増）と所要時間（40%増）で、トークン数ではありません。また、ケースA（テストなし）も最終的には10問全問正解しており、「LLMの自己判断は信用できない」と単純に結論づけることもできませんでした。

興味深い副産物として、ケースAは命名規約違反のメソッド名`Count_Vowels`を正しい`countVowels`にリネームしていました（隠しテストの存在を知らないため、これが正しい修正だと判断）。一方ケースBは、隠しテスト側が`Count_Vowels`という名前で呼び出しているのを見て、**規約違反と認識しつつもリネームしませんでした**（テストを壊さないため）。これは5章で改めて触れます。

### 3-2. 実際の大規模タスクでの実測値

小規模実験では差が限定的でしたが、実際にこのセッションで実行した大規模タスク（数百件規模の静的解析指摘の解消など）の生ログを直接解析すると、様相はまったく違いました。

| タスク | ターン数 | コンテキストサイズ（開始→終了） |
| :--- | :--- | :--- |
| Java 17構文モダナイズ（正常完了） | 229 | 92,741 → 229,139 トークン |
| PMD重複コード検知（1回目、後に差し戻し） | 316 | 389,876 → 601,312 トークン |
| 型/重複コードガードレール構築（1回目は断片的な報告で中断） | 661 | 302,169 → 562,861 トークン |

各ターンのコンテキストサイズを実際にサンプリングすると、661ターンのタスクではおおよそ**線形**に増加していました（一部抜粋）。

```
turn   0: 302,169 トークン
turn  88: 351,093 トークン
turn 220: 414,317 トークン
turn 352: 461,244 トークン
turn 484: 493,899 トークン
turn 616: 543,345 トークン
turn 660: 562,861 トークン（最終）
```

ここで重要なのは、**1ターンあたりのコンテキストサイズは線形に増えているだけ**という点です。しかし、Agentic Loopのアーキテクチャ上、各ターンで「その時点までの全履歴」を毎回まるごと再送信するため、**タスク全体で実際に処理された総トークン量**は、各ターンのコンテキストサイズを661ターン分すべて合計した値になります。実測すると：

> 661ターンの合計処理トークン量：**293,298,572トークン**（約2.93億トークン）
> 最終ターン単体のコンテキストサイズ：562,861トークン
> → 合計処理量は、最終ターンのコンテキストサイズの**約521倍**

ただし、この521倍という数字を「2乗成長の証拠」と単純に読むのは早計です。661ターン全体で見ると、661という数字そのものに近すぎて、素直な線形増加でも説明できてしまうからです。実際に内訳を分解すると：

> 開始時点の固定コンテキスト（30万トークン）× 661ターン分の再送信 ＝ **約2.0億トークン（68.1%）**
> 会話が進むにつれて履歴が積み上がっていく「成長分」＝ **約0.9億トークン（31.9%）**

つまり、この爆発の**主因は「2乗成長」ではなく、大きな固定コンテキストを何百回も律儀に再送信し続けたこと**でした。システムプロンプト・ツール定義・詳細なタスク指示からなる約30万トークンの土台が、それ自体はほとんど変わらないまま661回送り直されている——これだけで合計の約7割を占めます。残り3割が、会話履歴が積み上がっていく本来の意味での「成長分」で、こちらは1ターンあたりの増分が積み重なる分、ターン数が増えるほど加速度的に効いてきます（線形に増える数列を全項合計すればn²のオーダーになる、という算数の帰結です）。トークン爆発は、この2つの異なる性質のコストが合わさって起きています。

**そして重要な事実として、このタスクは`./scripts/ci-harness.sh`という静的ガードレールの下で動いていました。** つまり、静的ガードレールがあってもこの爆発は起きています。しかも1回目の試行は、661ターンの途中で報告が断片的になり、静的ゲートをPASSしないまま未完了の状態で私が引き取りました。静的ガードレールは、この爆発を防いでいません。

### 3-3. 考察：静的ガードレールの本当の価値はどこにあるか

3-1と3-2を合わせて見ると、当初の仮説（静的ガードレールがあればトークン爆発を防げる）は**誤りでした**。爆発は静的ガードレールの有無に関わらず起こります。タスクの複雑さがそのままターン数に跳ね返り、ターン数が増えるほど「固定コンテキストの反復送信」と「履歴の累積」の両方が効いてコストが膨らむためです。

では静的ガードレールは何のためにあるのか。3-2の失敗例が答えを示しています。1回目の試行の報告が断片的になったとき、私が「これは未完了だ」と確実に判断できたのは、`./scripts/ci-harness.sh`という**機械的な合否定義**があったからです。もしこれがなく、エージェント自身の「だいたい終わったと思います」という申告だけが判断材料だったら、実際には未完了なのに完了したと誤認していたかもしれません（実際、前回記事ではまさにこの誤認——PMD CPD検知139件を実質修正ゼロの抑制コメントで済ませて「解消しました」と報告してきた例——が起きています）。

同じ機械的な合否定義は、逆方向——エージェントが完了を過小申告するのではなく、気づかないままバグを埋め込む方向——にも効きます。前回記事では、`ReferenceEquality`指摘の一括置換で、エージェントが唯一null許容の`DateTimeFormatter.iZone`フィールドを単純な`.equals()`に置き換えてしまい、`ExceptionInInitializerError`（NPE起因）を引き起こしていますが、これも`./scripts/ci-harness.sh`のビルド＋テストがその場で検知し、`Objects.equals()`への修正につながっています。過小申告（CPDの例）と実装ミス（NPEの例）という性質の異なる2種類の失敗を、同じ「機械的な合否判定」という一つの仕組みで捕まえられたことになります。

つまり静的ガードレールが提供するのは、**爆発しない保証ではなく、収束できたかどうかを機械的に判定できるという保証**です。爆発そのものへの対策は、次章で扱う「コンテキストのリセット」など、別の設計が必要になります。

### 3-4. 本検証の限界

ここまでの数字は実測に基づいていますが、一般化するには注意が必要です。

- **3-1の対照実験は、ケースA・Bともに1回きりの試行です。** 統計的な再現性は確認していません。1.6%というトークン消費量の差は、複数回試行すれば結果が入れ替わる程度の誤差である可能性を排除できていません。
- **3-2の「固定コンテキスト68.1%／成長分31.9%」という内訳は、このセッションで使っていた特定のシステムプロンプト・ツール定義・タスク指示の大きさに強く依存した数字です。** 固定コンテキストがもっと小さいエージェント基盤や、履歴を自動的に要約・圧縮する実装では、この比率は大きく変わり得ます。「Agentic Loopは一般にこの比率で爆発する」と読み替えるのは行き過ぎです。
- **3-2で挙げた3つの大規模タスクは、対照実験ではなく、内容も規模も異なる実タスクの実測値です。** 条件を揃えて比較したものではないため、ここから得られる知見はこのセッション固有のケーススタディとして扱うべきで、他のプロジェクトや他のAgentic Loop実装にそのまま当てはめられる保証はありません。
- **661ターンのタスクで報告が断片的になった直接の原因は、ログを調べても特定できませんでした。** 本記事中で触れている「エージェント自身のリソース制約」という表現は仮説であり、確認された事実ではありません。
- **3-1の比較は「CIガードレールあり」と「LLMの自己判断のみ」の2択に限られます。** そもそも静的ガードレールの目的はトークン削減ではなく品質担保であり、これは前提として動かせません。今回はたまたま両ケースとも隠しテスト10/10で同等の品質に到達しましたが、これは実験対象が小規模だったことによる偶然の一致に近く、一般には「LLMの自己判断のみ」で同等の品質に到達できる保証はありません。また、CI以外の方法（人間によるレビュー、より詳細な自己検証指示、静的解析のみで動的テストは省く等）で同等の品質を担保した場合にトークンがどうなるかは、この実験だけでは分かりません。ケースBのトークン消費量が僅差だったことは「ガードレールを使ってもトークンはさほど増えない」ことを示すに過ぎず、「ガードレール以外の品質担保手段と比べて有利」であることを示すものではありません。

同一条件での複数回試行や、別のエージェント基盤での追試による再現性の確認は、今後の課題です。

## 4. 静的ガードレールによる設計アプローチ

- **コンテキストのリセットと外部状態への進捗の切り出し**：トークン爆発の根本原因は、会話履歴を毎ターン再送信するアーキテクチャそのものです。静的ガードレールはこれを解決しません。対策は、進捗をGitのコミットのような外部の永続状態に逃がし、会話の文脈自体を定期的にリセットすることです。次のターン（あるいは次のエージェント）は、肥大化した会話履歴を読み返す代わりに`git log`・`git diff`を読めば、記憶を保ったまま文脈だけ小さく再開できます。

  ただし、**効果は限定的**です。3-2の内訳（固定コンテキストの反復送信68%、履歴の成長分32%）を踏まえると、分割で削減できるのは成長分だけです。必要な作業量（≒ターン数）自体は分割しても変わらないため、固定コンテキストを毎ターン送り直すコスト（約2.0億トークン）はほぼ丸ごと残ります。実際に661ターンを10分割（約66ターンずつ）した場合の削減効果を計算し直すと：

  > 成長分（約0.9億トークン）が理論上1/10に圧縮：約0.9億 → 約940万トークン
  > 固定コンテキスト分（約2.0億トークン）はほぼ変わらず
  > 合計：293,298,572 → 約2億900万トークン（**削減率は約29%**）

  さらに、新しいエージェントを起こすたびに、システムプロンプト・ツール定義・タスクの説明・現状把握のための`git log`/`git diff`読み込みといった**固定費**が実際に発生します（実測では9万〜39万トークン）。これは上記の「固定コンテキスト」とほぼ同じ性質のコストで、分割を増やすほど積み上がります。つまり**分割で削減できるのは成長分の32%が上限で、それ以上細かく分割してもむしろ損になる領域がある**、というのが正確な結論です。この上限を踏まえると、分割よりも効くのは、**そもそも固定コンテキスト自体を小さくする**（タスク指示を簡潔にする、不要なツール定義を減らす等）ことや、**タスクを小さく保って必要なターン数自体を減らす**ことです。加えて、リセットのたびに「なぜその実装を選んだか」という推論の文脈も失われるため、新しいエージェントが同じ調査をやり直すという、トークン数には現れない質的なコストも発生します。目安としては、「外部状態（gitコミット）だけで次のエージェントが迷わず引き継げる、意味のあるまとまり」——ちょうど良いコミットの粒度と同じ感覚が実務的です。

  実際、このセッションでは「Java 17構文モダナイズ」「厳格な型/静的解析ガードレール構築」「PMD CPD対応」「恒久テスト追加」という4つの作業（いずれも第2弾記事で扱った内容）を、それぞれ独立した新規エージェント呼び出しに分け、間をgitコミットで引き継ぐという形で、ファイル単位でも1指摘単位でもない、この程度の粒度を自然に実践していました。唯一の例外が、まさに2.93億トークンを記録したタスクで、1回目の報告が断片的になった際に**会話を`SendMessage`で継続して再開した**ことです。もしあのとき会話を再開する代わりに新規エージェントを立て、`git status`・`git diff`から続きを把握させていれば、コストはさらに抑えられたはずです。
- **状態遷移の固定**：ループの終了条件（`./scripts/ci-harness.sh`が exit 0 になる等）をプログラム側で厳格に定義し、LLMの「もう十分でしょう」という主観的判断に委ねない。3章で見た通り、この停止条件があったからこそ、661ターンのタスクの「未完了」を明確に検知し、正しく再開できました。
- **決定論的フィルタリング（そして、その罠）**：LLMに渡すエラーログは最小化・差分化すべき、というのが定石です。しかし今回のセッションでは、逆の失敗も経験しました。javacはデフォルトで警告表示を100件で打ち切る（`-Xmaxwarns`のデフォルト値）ため、最初の実行では「40件の警告」しか見えず、実際には412件が隠れていました。**フィルタリング・要約は諸刃の剣で、意図せず問題の全体像を隠してしまうことがある**という点は、設計上の重要な注意点です。
- **動的（LLM）と静的の役割分担**：動的側は「このコードは意味的に正しいか」「この変換は安全か」といった意味論的判断、静的側は「型は合っているか」「テストは通るか」「重複はないか」といった形式検証とコスト制御を担う、という分担が実務的でした。3-1の`Count_Vowels`問題（規約違反と認識しつつも、テストを壊さないためリネームを見送った判断）は、まさにこの意味論的判断を動的側に委ねた一例です。詳しくは5章で扱います。

## 5. 静的ガードレールの限界領域と注意点

3-1の対照実験で観察した「`Count_Vowels`問題」は、静的ガードレールの限界を端的に示しています。**静的ゲート（この場合は固定されたテストスイート）は、ゲート自体が古い・不完全なインターフェースを暗黙に固定してしまうことがあります。** ケースBのエージェントは、命名規約違反を認識していながら、テストを壊さないためにあえて直しませんでした。これは合理的な判断ですが、「静的ガードレールを通過すること」と「コードとして最善であること」が食い違う具体例でもあります。

同様の現象は前回記事でも扱いました。PMD CPD（重複コード検知）ガードレールを導入した際、AIエージェントは139件の重複指摘すべてを、実質的な修正ゼロのまま抑制コメントで囲んで「解消しました」と報告してきました。これも「静的ゲートの通過」と「本来の目的の達成」が一致しなかった例です。静的チェックは**構文・型・既知のルールに対する逸脱**は機械的に検出できますが、「もっともらしいが実は目的を達成していない」という**意味論的な誤り**までは防げません。過剰な静的制約はエージェントの柔軟性そのものを削ぐため、どこまで固定してどこから任せるかのバランスは、タスクごとに人間が判断する必要があります。

## 6. おわりに

- Agentic Loopのコストは、1ターンあたりで見れば穏やかでも、タスク全体では単純な線形増加をはるかに超えて膨らみます。実測では、661ターンのタスクの合計処理トークン量が、最終ターン単体の521倍でした。ただしこの内訳の約7割は「大きな固定コンテキストを毎ターン律儀に再送信し続けたこと」で、正味の「2乗成長」に相当する部分は残り3割程度です。
- **静的ガードレールは、この爆発を防ぎません。** 2.93億トークンを記録したタスクは、まさに静的ゲートの下で発生しており、1回目の試行はそのゲートをPASSしないまま報告が断片的になり、私が引き取って再開しています（この中断の直接の原因は、ログを調べても特定できませんでした）。小規模な対照実験でも、ガードレールの有無によるその場のトークン消費量の差はごくわずかでした。静的ガードレールの本質的な価値は、コストの削減ではなく、**完了を機械的に定義し、収束できなかったことを確実に検知できる**という点にあります。爆発そのものへの対策は会話のリセットと外部状態への進捗切り出しが直接効きますが、削減できるのは成長分だけで、固定コンテキストの反復送信コストは分割しても残るため、効果は限定的です（10分割しても総コストは約29%減にとどまります）。より効くのは、固定コンテキスト自体を小さくすることです。
- ただし静的ガードレールは万能ではありません。固定されたテストやルールが、かえって古いインターフェースを温存させたり、「形式は満たすが目的は達成していない」近道をエージェントに許してしまうことがあります。「賢いLLM」に丸投げするのでも、「賢い外枠」だけに頼るのでもなく、**思考（動的）と構造（静的）を分離した上で、両方を人間が設計し、結果を独立に検証し続ける**ことが、Agentic Loopを実務で使いこなす上での現実的な落としどころだと考えています。
